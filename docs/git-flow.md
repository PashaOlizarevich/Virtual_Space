# Жизненный цикл задач и Git Workflow

Этот workflow обязателен для разработки новой функции, рефакторинга и исправления ошибки. Для read-only анализа, обсуждения и проверки без изменений создавать ветку и коммиты не требуется.

## 1. Инициализация

1. Проверь `git status --short` и текущую ветку командой `git branch --show-current`.
2. Не изменяй код напрямую в защищённых ветках: `main`, `master`, `dev`.
3. Проверь незакоммиченные изменения. Не смешивай изменения пользователя с новой задачей.
4. Выбери режим изоляции до первого изменения файлов.

### Сценарий A — параллельная работа

Используй Git worktree, если работа делегирована субагентам, другой процесс уже изменяет файлы в текущем каталоге или независимые части задачи выполняются одновременно.

Каждый исполнитель работает в отдельной папке worktree и отдельной ветке. Нельзя назначать двум исполнителям одну ветку или один worktree.

### Сценарий B — одиночная работа

Если задача выполняется одним агентом последовательно, создай отдельную ветку в текущем каталоге и работай только в ней.

## 2. Названия веток

Используй строчные латинские буквы, цифры и дефисы:

- `feature/<short-name>` — новая функция;
- `fix/<short-name>` — исправление ошибки;
- `refactor/<short-name>` — рефакторинг без изменения поведения;
- `chore/<short-name>` — конфигурация, документация или обслуживание проекта;
- `test/<short-name>` — изменения только тестов.

Название должно отражать одну задачу. Не используй пробелы, кириллицу и общие имена вроде `changes` или `work`.

## 3. Атомарные коммиты

Работай итеративно и создавай коммит после каждого завершённого и проверенного логического блока: схема данных, серверный контракт, UI-блок или тесты.

Не создавай коммит для незавершённого или заведомо неработающего состояния, кроме явно обозначенного диагностического savepoint по просьбе пользователя.

Формат сообщения:

```text
<type>(<optional-scope>): <short imperative description>
```

Допустимые типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`.

Перед каждым коммитом:

1. Проверь статус и staged diff.
2. Добавь только файлы логического блока.
3. Запусти релевантные проверки.
4. Проверь отсутствие секретов и временных артефактов.

## 4. Завершение и review

1. Запусти доступные тесты, lint, typecheck и сборку в объёме задачи.
2. Проверь итоговый diff и рабочее дерево.
3. Обнови проектную память по `.codex/rules/completion.md`.
4. Создай финальный коммит, если имеются незакоммиченные изменения задачи.
5. Остановись и предоставь отчёт: ветка, коммиты, файлы, проверки и ограничения.

Для сценария B заверши отчёт вопросом:

> Фича реализована. Проверяем работу, или я могу выполнить слияние (merge) с главной веткой?

Для сценария A заверши отчёт вопросом:

> Изолированная работа завершена. Могу ли я слить ветку в main и удалить временный worktree?

## 5. Слияние

- Никогда не выполняй merge, push, rebase, удаление ветки/worktree или создание Pull Request до прямого текстового разрешения пользователя.
- Фраза `Да, сливай` разрешает только ранее описанное слияние и связанные с ним безопасные действия.
- Перед merge повторно проверь целевую ветку, чистоту рабочего дерева и состояние рабочей ветки.
- При конфликте слияния остановись и опиши конфликт.
- После merge не удаляй рабочую ветку или worktree без разрешения, если пользователь не включил это действие в команду.
