# Решения для первого DB-релиза

## 1. Назначение

Документ подробно раскрывает пункт 23 из `docs/implementation-plan.md` и объясняет решения, которые
должны оставаться неизменными при проектировании первой Prisma schema, миграций и серверных
контрактов Virtual Space.

Это единый подготовительный архитектурный документ для полных описаний решений из
`docs/implementation-plan.md`, относящихся к первому DB-релизу. Каждый выполненный пункт этого этапа
добавляется в данный файл отдельным блоком с обязательным заголовком `Пункт N — название`, после
которого идут назначение, принятые решения, обоснование, последствия и критерии соблюдения. Отдельный
документ на каждый пункт не создаётся.

Документ не означает, что PostgreSQL, Prisma-модели, миграции, Auth.js или production API уже
реализованы.

Под первым DB-релизом здесь понимается общий первый backend/data milestone, включающий foundation,
каталог, административную identity и заказы в последовательных миграциях, а не обязательно один
production deploy.

## Пункт 23 — Решения первого DB-релиза

### 23.1. Что было сделано

Для первого DB-релиза зафиксированы четыре границы:

1. заказ использует пять статусов: `NEW`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`;
2. товар конфигурируется через группы и значения опций без отдельных SKU-вариантов;
3. деньги хранятся точно как PostgreSQL `numeric` и Prisma `Decimal`, а наружу передаются
   decimal-строкой с валютой `BYN`;
4. Auth.js сначала защищает административный сценарий, а пользовательские аккаунты и серверная
   корзина относятся к следующему этапу.

Эти решения синхронизированы с `docs/architecture.md`. Последующие пункты плана должны реализовывать
их, а не повторно выбирать доменную модель.

### 23.2. Статусы заказа

#### Принятый контракт

Prisma enum и серверный доменный тип должны содержать только:

```text
NEW
CONFIRMED
IN_PROGRESS
COMPLETED
CANCELLED
```

Основной последовательный поток:

```text
NEW -> CONFIRMED -> IN_PROGRESS -> COMPLETED
```

Отмена разрешена из `NEW`, `CONFIRMED` и `IN_PROGRESS`. `COMPLETED` и `CANCELLED` являются
терминальными состояниями. Любой другой переход отклоняется серверным service-слоем.

Каждое изменение должно атомарно обновлять `Order.status` и добавлять `OrderStatusHistory` с
предыдущим и новым статусом, временем и optional идентификатором администратора.

#### Зачем

- `CONFIRMED` отделяет принятую заявку от новой и ещё не проверенной.
- `IN_PROGRESS` описывает реальное исполнение заказа без неоднозначного общего `PROCESSING`.
- ограниченный граф переходов не позволяет вернуть завершённый или отменённый заказ в работу
  случайным запросом;
- история даёт аудит административных действий и не зависит от текущего значения заказа.

UI, middleware и знание URL не являются механизмом защиты. Сервер обязан проверить Auth.js session,
роль `ADMIN`, входной enum и допустимость перехода.

### 23.3. Товарные опции без SKU-вариантов

#### Принятый контракт

Первый релиз использует:

- `ProductOptionGroup` — стабильный идентификатор/ключ, подпись и порядок группы;
- `ProductOption` — стабильный идентификатор/ключ, подпись и порядок значения внутри группы.

Например, группа «Материал» может содержать значения «Дуб» и «Орех». Выбранные стабильные
идентификаторы передаются в корзину и сохраняются снимком в позиции заказа.

`ProductVariant` не создаётся. Комбинация и отдельное значение опции не имеют собственного SKU,
price modifier, отдельной цены или остатка. Цена и доступность определяются товаром, а сервер
повторно проверяет выбранные значения при создании заказа.

#### Зачем

- текущий каталог не требует складского учёта каждой комбинации;
- преждевременные варианты усложнили бы уникальные ограничения, остатки, корзину и миграции;
- группы и значения сохраняют нужную пользователю конфигурацию без фиктивных складских сущностей;
- стабильные идентификаторы позволяют безопасно заменить mock-данные постоянным хранилищем.

`ProductVariant` добавляется отдельной совместимой миграцией только при появлении реального правила:
комбинация получает собственный SKU, цену или остаток. До этого отсутствие вариантов является
осознанным ограничением, а не незавершённой моделью.

### 23.4. Деньги и публичный DTO

#### Хранение

Денежные поля PostgreSQL используют `numeric` с явно выбранными precision и scale. Их значения,
правило округления и допустимая грамматика канонической строки определяются в пункте 35 до создания
использующей их миграции. Prisma представляет деньги как `Decimal`. `float`, `double precision` и
JavaScript `number` не являются источником истины для цен и итогов.

Валюта первого релиза — `BYN` и хранится явно там, где значение должно оставаться самостоятельным
денежным снимком, включая заказ.

#### Граница сервера

Prisma `Decimal` не передаётся в Client Components или JSON напрямую. Mapper формирует безопасный
сериализуемый DTO:

```ts
type MoneyDto = {
  amount: string;
  currency: "BYN";
};
```

`amount` — каноническая decimal-строка без форматированных пробелов, символа валюты или локальной
запятой, например `"1299.90"`. Отображение в локали выполняет formatter, но вычисление total,
проверка цены и округление остаются на сервере.

#### Зачем

- двоичная арифметика JavaScript не гарантирует точное представление десятичных денежных значений;
- строка безопасно проходит через JSON и не раскрывает внутренний Prisma-тип;
- явная валюта исключает неявное предположение в API и снимках заказа;
- единый mapper позволяет постепенно заменить текущие frontend-цены типа `number`.

Клиентские цена, скидка и итог считаются недоверенными. При оформлении сервер перечитывает товары,
проверяет доступность и пересчитывает сумму по данным PostgreSQL.

#### Рассмотренные альтернативы

- PostgreSQL `float` и JavaScript `number` отклонены из-за ошибок двоичной арифметики.
- Хранение только minor units не выбрано: нормативным контрактом проекта остаётся decimal, а
  правила точности будут единообразно заданы в пункте 35.
- Передача Prisma `Decimal` напрямую отклонена, потому что публичный контракт не должен зависеть от
  ORM и её сериализации.

### 23.5. Первый этап Auth.js

#### Объём первого релиза

Auth.js сначала реализуется для администратора и защищает:

- административные маршруты;
- Server Actions и Route Handlers изменения товаров, заказов и настроек;
- смену статуса и другие привилегированные service entry points.

Каждая защищённая серверная операция самостоятельно проверяет session и роль `ADMIN`. Ранний
redirect в middleware и скрытие элементов UI могут улучшать интерфейс, но не заменяют авторизацию.

#### Что отложено

На следующий этап перенесены:

- публичная регистрация и пользовательский вход;
- профиль, собственные заказы и восстановление доступа;
- постоянные `Cart`/`CartItem` и объединение гостевой корзины с серверной.

До этого гостевая корзина остаётся версионированным клиентским состоянием и не считается доверенным
источником цены, наличия или прав. Отложенные пользовательские сценарии не должны блокировать
защищённую админку и гостевое оформление заявки.

#### Зачем

- административная поверхность уже требует настоящей серверной границы доступа;
- пользовательская авторизация добавляет отдельные требования к lifecycle аккаунта, восстановлению,
  ownership и синхронизации корзин;
- поэтапное внедрение уменьшает первый DB-релиз и не вынуждает принимать политику пользовательских
  данных раньше соответствующих пунктов плана.

Одновременное внедрение административной и покупательской авторизации отклонено как преждевременное
расширение scope. Постоянная гостевая корзина на сервере также не вводится до появления
пользовательской identity и правил объединения корзин.

### 23.6. Последствия для последующих пунктов

| Область               | Обязательное продолжение                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------- |
| Prisma foundation     | Настроить PostgreSQL и единый server-only PrismaClient без изменения решений этого документа |
| Каталог               | Создать `ProductOptionGroup` и `ProductOption`, не создавая `ProductVariant`                 |
| Денежный контракт     | Ввести общий `MoneyDto`, mapper из `Decimal` и formatter для UI                              |
| Заказы                | Создать enum из пяти статусов и атомарную историю допустимых переходов                       |
| Auth.js               | Сначала подключить администратора и server-side проверку роли                                |
| Пользовательский этап | Позже добавить аккаунты, ownership заказов, серверную корзину и безопасное объединение       |

Изменение любого из этих решений до реализации требует сначала обновить `docs/architecture.md`, этот
документ и связанные пункты плана, затем оценить совместимость миграции и frontend-контрактов.

### 23.7. Что не входит в пункт 23

- выбор PostgreSQL-платформы, pooling и release-процесс миграций — пункт 24;
- retention заказов, анонимизация пользователей и bootstrap первого администратора — пункт 25;
- Prisma config, schema и DB client — пункт 26;

### 23.8. Критерии соблюдения решения

При реализации последующих пунктов необходимо подтвердить:

- enum и server validation принимают ровно пять утверждённых статусов;
- недопустимые переходы отклоняются сервером и не создают частичную историю;
- option groups и options имеют стабильные идентификаторы, а `ProductVariant` отсутствует;
- schema использует `numeric`/`Decimal`, публичный DTO — decimal-строку и `BYN`;
- цена и total пересчитываются сервером, а Prisma-модели не выдаются наружу;
- административные операции проверяют действительную Auth.js session и роль `ADMIN` на сервере;
- пользовательские аккаунты и server cart не попадают в первый этап скрытым расширением scope;
- SQL каждой миграции просмотрен на потерю данных, блокировки и несовместимость развёртывания.

## Пункт 24 — PostgreSQL и развёртывание первого DB-релиза

### 24.1. Назначение

Раздел раскрывает пункт 24 из `docs/implementation-plan.md` и фиксирует платформу PostgreSQL,
изоляцию local/preview/production, connection pooling, доступ к секретам и release-процесс миграций.

Это подготовительное архитектурное решение. Оно не создаёт Neon/Vercel-ресурсы, не подключает
production-базу и не означает, что Prisma schema или миграции уже реализованы.

### 24.2. Принятое решение

- Next.js-приложение развёртывается на **Vercel**.
- Управляемый PostgreSQL размещается в **Neon** через Neon-managed Vercel Integration.
- Регион Neon выбирается максимально близко к региону Vercel Function, обслуживающему запросы к БД;
  конкретный регион фиксируется при создании ресурсов после проверки доступности для выбранного
  аккаунта и требований к размещению данных.
- Production использует долгоживущую защищённую Neon-ветку. Каждый preview deployment получает
  отдельную временную Neon-ветку. Local development использует отдельную dev-ветку, а не production.
- Приложение подключается через pooled URL; Prisma CLI, миграции, backup/restore и другое
  session-dependent администрирование используют direct URL.

Vercel Postgres как отдельный продукт не выбирается: новые PostgreSQL-базы подключаются через
Marketplace, а прежний Vercel Postgres был перенесён на Neon. Self-hosted PostgreSQL, Supabase,
Railway и Render не дают текущему Vercel-first проекту преимущества, оправдывающего дополнительную
операционную поверхность. Выбор провайдера можно пересмотреть до хранения production-данных, если
изменятся требования к региону, бюджету, SLA или юридическому размещению данных.

### 24.3. Матрица окружений

| Среда      | Приложение                   | PostgreSQL                                                    | Данные и жизненный цикл                                                                                  |
| ---------- | ---------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Local      | `npm run dev` на Node.js 24+ | отдельная Neon-ветка `dev/<developer-or-feature>`             | только тестовые/seed-данные; production credentials локально не выдаются                                 |
| Preview    | Vercel Preview на PR/ветку   | отдельная ephemeral Neon-ветка `preview/pr-<number>-<branch>` | создаётся до проверки миграции, получает собственные URLs, удаляется после закрытия PR по TTL/интеграции |
| Production | Vercel Production из `main`  | защищённая Neon-ветка `production`                            | реальные данные; запрет reset, auto-seed и использования из preview/local                                |

Preview не должен автоматически получать необработанную копию production-данных. До появления
процесса маскирования preview создаётся от безопасной непроизводственной baseline-ветки и заполняется
повторяемым seed. Если для диагностики позже потребуются реалистичные данные, источником может быть
только предварительно анонимизированная ветка с отдельно утверждёнными правилами доступа и retention.

### 24.4. Соединения и pooling

Neon выдаёт два server-only секрета:

```dotenv
DATABASE_URL=             # pooled endpoint, hostname содержит -pooler
DATABASE_URL_UNPOOLED=    # direct endpoint для release/admin tooling
```

Правила использования:

1. `DATABASE_URL` использует PrismaClient через `@prisma/adapter-pg` для всех runtime-запросов Vercel
   и local/preview приложения. В каждой среде URL указывает только на её Neon-ветку.
2. `DATABASE_URL_UNPOOLED` используется `prisma.config.ts` для `prisma migrate deploy`, разработки
   миграций, introspection, backup/restore и Prisma Studio. Runtime-код его не читает.
3. PrismaClient остаётся единым server-only singleton на процесс/warm instance. Нельзя создавать
   новый client на каждый запрос или подключать direct URL к serverless runtime.
4. Neon PgBouncer работает в transaction mode. Код не полагается на сохранение session-level
   `SET`, временных таблиц, `LISTEN/NOTIFY`, session advisory locks или cursors между транзакциями.
5. Транзакции должны быть короткими и не содержать сетевых вызовов. Исчерпание пула, время ожидания,
   число соединений и медленные запросы контролируются метриками Neon; размер compute/pool меняется
   по измеренной нагрузке, а не предварительно.
6. Оба URL обязаны требовать TLS согласно строкам подключения Neon. Параметры URL не собираются из
   отдельных фрагментов в коде и не логируются.

Хотя актуальные Prisma и Neon допускают часть CLI-операций через pooler, для release-процесса выбран
direct endpoint: это отделяет ограниченный административный доступ от массового serverless-трафика и
не зависит от session-ограничений transaction pooling.

### 24.5. Секреты и права доступа

- Значения хранятся только в Neon/Vercel secret storage или в локальном gitignored `.env.local`;
  репозиторий содержит лишь пустые имена в `.env.example`.
- `DATABASE_URL` доступен runtime-окружению соответствующего Vercel deployment. Он не имеет
  `NEXT_PUBLIC_`-префикса и никогда не передаётся в Client Components, ответы или логи.
- `DATABASE_URL_UNPOOLED` доступен только локальному доверенному оператору и отдельному migration job.
  Обычным Preview/Production Functions direct credential не требуется.
- Production и non-production используют разные credentials. Preview credential ограничен своей
  ephemeral-веткой; закрытие PR отзывает доступ удалением ветки/endpoint.
- Доступ людей выдаётся по принципу минимальных привилегий через Neon/Vercel accounts, с MFA для
  владельцев production и аудитом участников. Строки подключения ротируются после подозрения на
  раскрытие или изменения состава привилегированной команды.
- CI не печатает env, строки команд с URL, Prisma debug output с credentials и полные ошибки
  подключения. Проверка env сообщает только имя отсутствующей переменной.

### 24.6. Release-процесс миграций

Миграция является отдельным одноразовым release job и не запускается во время `next build`, старта
приложения, Server Action, Route Handler или serverless cold start.

#### Pull request / preview

1. Создать из безопасной baseline отдельную Neon preview-ветку и внедрить в deployment её pooled и
   direct URLs.
2. Установить зависимости через `npm ci`; выполнить `prisma validate` и `prisma generate`.
3. Прочитать SQL новой миграции и проверить `DROP`, сужение типа, table rewrite, `NOT NULL` без
   backfill, длительные блокировки, повторный запуск и совместимость старого/нового приложения.
4. Одноразово выполнить `prisma migrate deploy` через `DATABASE_URL_UNPOOLED` только на preview-ветке.
5. Выполнить тесты и сборку приложения против preview; seed запускать только явной отдельной командой.

#### Production

1. До релиза подтвердить backup/restore или точку восстановления и успешную проверку той же
   неизменённой миграции на preview/непроизводственной копии.
2. Остановить rollout при failed checks, drift, unresolved failed migration или отсутствии direct
   production credential у migration job.
3. Выполнить ровно один `prisma migrate deploy` с immutable commit/artifact через
   `DATABASE_URL_UNPOOLED`; job не принимает запросы пользователей и не запускает seed.
4. После успеха развернуть совместимую версию приложения и выполнить smoke-проверку. При ошибке
   приложения откатить код только если схема обратно совместима; миграцию не откатывать вручную.
5. Исправлять ошибку forward-fix миграцией. Для несовместимых изменений использовать отдельные
   релизы `expand -> migrate/backfill -> contract`; destructive contract требует отдельного
   подтверждения после переключения всех потребителей.

Одновременные production migration jobs запрещены. CI/CD должен сериализовать их через один
environment lock/concurrency group. `prisma migrate dev`, `prisma db push`, reset и автоматический
seed в production запрещены.

### 24.7. Критерии соблюдения

- local, каждый preview и production имеют изолированные Neon-ветки и credentials;
- runtime читает pooled `DATABASE_URL`, а release job — direct `DATABASE_URL_UNPOOLED`;
- preview/local не имеют production credentials и не содержат немаскированные production-данные;
- миграция проверена на preview и выполняется один раз до production rollout;
- cold start, build и обычный runtime никогда не применяют миграции;
- backup/restore, serialisation migration jobs и forward-fix определены до первого production deploy;
- секреты не попадают в Git, клиентский bundle, логи и deployment artifacts.

## Пункт 25 — жизненный цикл заказов, аккаунтов и первого администратора

### 25.1. Назначение и границы

Раздел раскрывает пункт 25 из `docs/implementation-plan.md`. Он задаёт инварианты для будущих
Prisma-моделей, `onDelete`, сервисов удаления аккаунта и команды bootstrap, но не создаёт schema,
миграции, Auth.js-конфигурацию, production-данные или администратора.

Политика исходит из текущего размещения магазина в Беларуси. До начала production-продаж владелец
магазина обязан подтвердить применимый перечень документов и сроки с бухгалтером или юристом. Если
закон, договор, спор, возврат, налоговая проверка или legal hold требуют более долгого хранения, они
имеют приоритет над автоматическим удалением.

### 25.2. Хранение заказов

- `Order`, `OrderItem` и `OrderStatusHistory` являются самостоятельной историей хозяйственной
  операции и не удаляются вместе с аккаунтом покупателя, администратора или товаром.
- Для первого production-релиза применяется консервативный срок: **10 лет после окончания
  календарного года, в котором заказ завершён или отменён**. До юридического подтверждения нельзя
  настраивать меньший срок. Незавершённый заказ отсчитывает срок только после перехода в терминальный
  статус `COMPLETED` или `CANCELLED`.
- Заказ хранит неизменяемые снимки товарных данных, цены, валюты и выбранных опций. Контактный снимок
  покупателя хранится только в объёме, необходимом для исполнения заказа, претензий и обязательного
  учёта; маркетинговое согласие и аналитический профиль в заказ не копируются.
- После срока хранения периодическая server-only job необратимо удаляет или анонимизирует прямые
  идентификаторы покупателя и свободный комментарий. Денежная сумма, валюта, позиции, статусы и
  обезличенные временные данные могут остаться для финансовой отчётности и агрегированной аналитики,
  если по ним нельзя разумно восстановить личность.
- Legal hold блокирует purge только для явно отмеченных заказов, содержит причину и срок пересмотра и
  доступен ограниченной административной роли. Hold нельзя использовать как бессрочный режим по
  умолчанию.
- Purge выполняется повторяемыми ограниченными пакетами, ведёт аудит количества и идентификаторов
  обработанных записей без записи удалённых персональных данных в логи. Backup наследует тот же
  срок: данные исчезают из активной БД сразу по политике, а из резервных копий — по их ограниченному
  циклу ротации и не восстанавливаются обратно в active storage без повторного purge.

### 25.3. Удаление и анонимизация пользовательского аккаунта

Удаление аккаунта является серверной доменной операцией, а не каскадным `DELETE User`:

1. Повторно проверить действующую сессию, владение аккаунтом и подтверждение чувствительной операции.
2. В одной транзакции отозвать активные сессии, удалить `Account`, `Session`,
   `VerificationToken`, recovery credentials и активную корзину с позициями.
3. Не удалять заказы. Установить их optional `userId` в `NULL`, сохранив минимальный контактный
   снимок заказа до окончания его отдельного retention-срока.
4. Обезличить `User`: заменить email случайным непубличным уникальным значением, удалить имя,
   телефон и прочие необязательные поля, уничтожить password hash, установить `deletedAt` и запретить
   вход. Исходные значения, обратимый mapping и зашифрованная копия не сохраняются.
5. Записать технический audit event без прежнего email, телефона, session token и содержимого заказа.

Простой soft delete с сохранением профиля отклонён: он прекращает вход, но не достигает минимизации
персональных данных. Каскадное удаление заказов также отклонено, поскольку разрушает историю
операций. Повторная регистрация с прежним email создаёт новую identity и не возвращает старые заказы
автоматически; связывание возможно только отдельным проверенным процессом, если он будет утверждён.

Запрос на удаление может быть частично ограничен обязательным хранением заказа. Пользователю нужно
сообщить, какие категории данных удалены немедленно, какие сохранены, на каком основании и до какого
события. До реализации пользовательских аккаунтов текст privacy notice и фактическая процедура
должны быть согласованы с этой политикой.

### 25.4. Первый администратор

Первый `ADMIN` создаётся только отдельной одноразовой server-only CLI-командой из immutable
release artifact на доверенной машине или в вручную запущенном защищённом job:

- команда подключается к нужной БД через direct `DATABASE_URL_UNPOOLED`; URL находится в secret
  storage и не передаётся аргументом;
- email вводится интерактивно или через защищённую переменную job, пароль — только скрытым
  интерактивным prompt либо masked secret input. Пароль запрещено передавать CLI-аргументом,
  записывать в shell history, `.env.example`, seed, fixture, логи или репозиторий;
- ввод валидируется, пароль хешируется актуальной password-hashing функцией с индивидуальной солью;
  в БД сохраняется только hash. Конкретная библиотека и параметры выбираются в пункте 43 после
  проверки актуальной версии Auth.js и среды выполнения;
- транзакция берёт фиксированный PostgreSQL transaction-level advisory lock для bootstrap, затем с
  уникальным email создаёт пользователя с ролью `ADMIN` только если администраторов ещё нет. При
  наличии хотя бы одного `ADMIN` команда завершается без изменений; lock исключает создание двух
  первых администраторов с разными email при параллельном запуске;
- роль никогда не принимается из публичной регистрации, profile API или client input. Следующих
  администраторов создаёт уже аутентифицированный `ADMIN` отдельной защищённой операцией;
- успешный bootstrap пишет минимальный audit event (`actor=SYSTEM`, новый user id, время, request/job
  id), но не email и не credential. Ошибки не выводят connection string, password или hash;
- после создания оператор проверяет вход, ротирует временный пароль, если он был выдан через job
  secret, и удаляет одноразовый secret из окружения. Повторный запуск остаётся безопасным no-op.

Production seed не создаёт пользователей и не читает admin credentials. Миграция также никогда не
создаёт администратора: schema rollout и privileged identity имеют разные права, журнал и жизненный
цикл. Break-glass восстановление доступа требует отдельной документированной ручной процедуры с MFA
у инфраструктурного аккаунта и не ослабляет проверку «администратор уже существует» в обычной
bootstrap-команде.

### 25.5. Последствия для схемы и сервисов

| Область              | Обязательное продолжение                                                                            |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `Order`              | Optional `userId`; снимок покупателя и `retentionUntil`; отсутствие cascade от `User`               |
| `OrderStatusHistory` | Optional actor admin; удаление admin не разрушает историю переходов                                 |
| `User`               | `deletedAt`, nullable/anonymizable profile, уникальная identity без обратимого mapping              |
| Auth.js              | Сессии и связанные credentials удаляются при anonymization; роль задаёт только сервер               |
| Cart                 | Каскадно удаляется с аккаунтом; заказ от корзины не зависит                                         |
| Retention job        | Server-only, пакетная, идемпотентная, учитывает legal hold и backup lifecycle                       |
| Bootstrap            | Отдельная CLI-команда; direct DB secret, скрытый password input, transaction lock, безопасный no-op |

Точные имена полей могут быть уточнены при проектировании schema, но перечисленные отношения,

### 25.6. Проверки реализации

- удаление пользователя отзывает вход, удаляет корзину и credentials, но сохраняет заказ и его
  позиции;
- после анонимизации ни один пользовательский endpoint, лог или audit event не раскрывает прежние
  email, телефон, имя или session data;
- FK `Order.userId` и actor истории допускают `NULL`/`SetNull`, а заказ не использует cascade delete;
- purge не трогает записи до `retentionUntil`, пропускает legal hold и безопасно повторяется;
- backup restore не возвращает просроченные персональные данные в активную эксплуатацию;
- bootstrap не принимает роль с клиента, не содержит фиксированного пароля и не печатает секреты;
- два параллельных запуска создают не более одного первого администратора;
- повторный запуск после успеха завершается без изменения существующих пользователей;
- seed, миграции, Git history и deployment logs не содержат admin credentials.

Реализован недеструктивный schema-only фундамент без доменных таблиц и без миграции:

## Пункт 27 — модели каталога и настроек магазина

В `prisma/schema.prisma` созданы семь самостоятельных валидных каркасов доменных моделей:

| Модель                 | Назначение в первом DB-релизе                                                       |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `Category`             | Категория общего каталога, с которой позднее связываются товары                     |
| `Product`              | Основная запись товара и будущий источник истины для цены, остатка и публикации     |
| `ProductImage`         | Упорядоченное изображение галереи товара и будущая ссылка на Cloudinary             |
| `ProductSpecification` | Отдельная именованная характеристика товара                                         |
| `ProductOptionGroup`   | Группа выбираемых свойств товара без создания SKU-варианта                          |
| `ProductOption`        | Допустимое значение внутри группы опций                                             |
| `StoreSettings`        | Постоянное хранилище основной или именованной конфигурации магазина и его контактов |

Каждая модель на этом шаге содержит только обязательный для валидной Prisma-модели первичный ключ
`id BigInt @id @default(autoincrement())`. Последовательный PostgreSQL `bigint identity` выбран как
компактный локальный ключ для одной базы данных: он не требует расширения UUID, сохраняет хорошую
локальность B-tree и оставляет публичные `slug`, номера и DTO-идентификаторы независимыми от
внутреннего ключа. При передаче такого id через JSON server mapper обязан преобразовать Prisma
`BigInt` в строку; Prisma-модель напрямую публичным DTO не является.

Изменение классифицировано как недеструктивное `schema-only`: до пункта 27 доменных таблиц не было,
существующие поля и данные не удаляются и не преобразуются. SQL-миграция намеренно не создана,
`prisma db push`, подключение к PostgreSQL и seed не запускались. Фактические таблицы появятся только
в отдельной версионируемой миграции после завершения относящихся к ним требований схемы.

## Пункт 28 — обязательные поля и связи каталога

Каркасы каталога расширены до предметной Prisma-схемы. `Category` и `Product` получили обязательные
нормализованные slug в формате lowercase kebab-case и глобальные unique-ограничения. Нормализация
выполняется до записи на серверной границе; база гарантирует уникальность уже канонического значения.
Публичный маршрут товара поэтому остаётся независимым от внутреннего `BigInt` id.

`Product` хранит обязательные `categoryId`, название, описание, материал, стиль и размеры, точную цену
`Decimal(12, 2)`, enum-валюту `BYN`, целочисленный остаток, состояние публикации `isActive`, nullable
`newFrom`/`newUntil` как PostgreSQL `timestamptz(3)`, а также `createdAt`/`updatedAt`. Остаток по умолчанию
равен нулю, новый товар по умолчанию не опубликован. Ограничения `price >= 0`, `stock >= 0` и
согласованности периода будут добавлены в SQL-миграции на предусмотренном планом этапе CHECK-ограничений;
до этого те же инварианты обязана проверять серверная команда записи.

Управление новинкой имеет один канонический контракт: выключенный переключатель записывает обе даты
как `NULL`; включённый требует начало и окончание, причём рекомендуемое окончание формы вычисляется как
начало плюс 30 календарных дней. Это UI/server default, а не DB default: PostgreSQL не должен зависеть
от момента вставки, если администратор выбрал другую дату. Публичный каталог считает новинку активной
только внутри включительного интервала `newFrom <= now <= newUntil`.

Дочерние записи получили обязательные FK и порядок: изображения содержат Cloudinary public id,
защищённый URL, alt и `position`; характеристики — label, value и `position`; группы и значения опций —
label и `position`. Категория защищена от удаления при существующих товарах (`Restrict`), а полностью
принадлежащие товару изображения, характеристики, группы и значения удаляются каскадно. Все сущности
каталога имеют timezone-aware timestamps. Стабильные ключи опций, составные unique-ограничения и
индексы остаются в пунктах 30–31, миграция — в пункте 32.

Изменение недеструктивное `schema-only`: таблицы ещё не создавались, SQL-миграция, подключение к БД,
`db push` и seed не выполнялись. `StoreSettings` не расширялся, поскольку пункт 28 ограничен каталогом.

## Пункт 29 — отсутствие товарных SKU-вариантов в первом релизе

Проверена и сохранена модель первого DB-релиза без `ProductVariant`. Цена, валюта, остаток и
доступность принадлежат `Product`; `ProductOptionGroup` и `ProductOption` описывают только допустимый
выбор покупателя. Ни отдельное значение, ни комбинация выбранных опций не имеют собственного SKU,
цены, модификатора цены или складского остатка.

Фактическая `prisma/schema.prisma` соответствует этому контракту: модель `ProductVariant`, ссылки на
неё и variant-таблицы отсутствуют, а каталог использует прямую связь
`Product -> ProductOptionGroup -> ProductOption`. Каталог миграций также не содержит SQL для
вариантов. Поэтому пункт не требует изменения схемы или создания пустой миграции.

`ProductVariant` можно добавить только отдельным последующим изменением, если появится подтверждённый
доменный инвариант: конкретная комбинация опций получает собственный SKU, цену либо остаток. Такое
изменение должно быть совместимым `expand`-шагом: новая таблица и nullable-связи создаются отдельной
версионируемой миграцией, существующие товары продолжают работать по товарной цене и остатку, а
переключение чтения и записи выполняется лишь после backfill и проверки данных. Пункт 29 не резервирует
схему такой таблицы и не предполагает скрытого variant id в текущих контрактах.

Классификация результата: подтверждение существующей schema boundary без изменения схемы и данных;
оно совместимо и недеструктивно. PostgreSQL не подключался, `prisma db push`, migration, seed и
backfill не выполнялись. Пункты 30–32 по стабильным ключам опций, ограничениям, индексам и первой
миграции остаются самостоятельными.

## Пункт 30 — стабильные идентификаторы товарных опций

В `ProductOptionGroup` и `ProductOption` добавлено обязательное строковое поле `key`. Внутренний
`BigInt id` остаётся первичным ключом и используется только для связей внутри PostgreSQL, а `key`
становится стабильным доменным идентификатором, который можно передавать в каталог и корзину и
сохранять в неизменяемом снимке позиции заказа.

Ключи задаются в каноническом lowercase kebab-case (`upholstery`, `leg-color`, `warm-beige`) и не
формируются из изменяемой пользовательской подписи автоматически. Область идентичности группы —
товар, область идентичности значения — группа: группа определяется парой `(productId, key)`, а
значение — парой `(groupId, key)`. Одинаковый ключ допустим у разных товаров или в разных группах.
После использования в корзине или заказе ключ нельзя переименовывать: новая смысловая опция получает
новый ключ, а отображаемый `label` можно менять независимо.

Публичные контракты называют эти значения `groupId` и `optionId` для совместимости с уже работающим
mock-каталогом, но server mapper должен заполнять их из `ProductOptionGroup.key` и
`ProductOption.key`, а не сериализовать внутренние `BigInt id`. Снимок заказа позднее сохраняет как
ключи, так и отображаемые подписи, чтобы история не зависела от изменений каталога.

Изменение классифицировано как совместимое недеструктивное `schema-only`: таблицы ещё не создавались,
данные и backfill отсутствуют, SQL-миграция, `db push` и seed не выполнялись. Составные
unique-ограничения для указанных областей идентичности намеренно относятся к пункту 31, а первая
версионированная миграция — к пункту 32.

## Пункт 31 — ограничения и индексы каталога и настроек

Схема закрепляет уникальность данных в тех же областях, в которых приложение их получает и
упорядочивает. Глобальные `Category.slug` и `Product.slug` остаются уникальными публичными
идентификаторами. Для изображений уникален Cloudinary public id, а позиция уникальна в пределах
товара. Для характеристик в пределах товара уникальны и подпись, и позиция. Для групп и значений
опций закреплены области стабильных ключей `(productId, key)` и `(groupId, key)`, а также уникальный
порядок `(productId, position)` и `(groupId, position)`. Эти составные unique-ограничения одновременно
дают PostgreSQL индексы с внешним ключом в первом столбце, поэтому отдельные дублирующие FK-индексы
для дочерних таблиц не создаются.

Публичный каталог получает активные товары в стабильном порядке `createdAt DESC, id DESC`; выборка
категории добавляет равенство по `categoryId`, поэтому для этих путей заданы отдельные составные
индексы. Выборка `/new` фильтрует опубликованные товары по включительному интервалу новинки и
сортирует по `newFrom DESC`; соответствующий индекс начинается с `isActive`, затем содержит
`newFrom`, `newUntil` и стабильный tie-breaker `id`. Категории сортируются по `name, id`. Индексы по
цене, материалу и стилю намеренно не добавлены: фактический server query и подтверждённая
селективность этих фильтров ещё отсутствуют, а преждевременные индексы увеличили бы стоимость записи.

`StoreSettings` получает стабильный уникальный строковый ключ с каноническим значением `primary` по
умолчанию. Серверный слой должен получать основную конфигурацию по этому ключу, а не предполагать
конкретное значение автоинкрементного `BigInt id`; это сохраняет возможность позднее добавить
именованные конфигурации без смены идентификатора основной записи.

Изменение классифицировано как совместимое недеструктивное `schema-only`: первая миграция каталога
ещё не создана, таблиц и данных для backfill нет. SQL-миграция, подключение к PostgreSQL, `db push` и
seed не выполнялись; создание и ручная проверка SQL остаются границей пункта 32.

## Пункт 32 — первая миграция каталога и настроек

Создана первая версионируемая Prisma-миграция
`20260830120000_create_catalog_and_settings`. Она получена офлайн как diff от пустой PostgreSQL-схемы
к текущей `prisma/schema.prisma` и создаёт enum `Currency`, таблицы каталога и `StoreSettings`,
первичные и внешние ключи, unique-ограничения и индексы пункта 31. `migration_lock.toml` фиксирует
провайдер `postgresql` для последующих миграций.

Изменение классифицировано как совместимое недеструктивное `schema-only`: это первая миграция, поэтому
она не меняет существующие таблицы каталога и не требует backfill. Ручная проверка SQL подтвердила
отсутствие `DROP`, `TRUNCATE`, удаления данных, сужения типов, `ALTER COLUMN` и добавления `NOT NULL`
к существующим таблицам. Обязательные поля создаются только вместе с новыми пустыми таблицами.

Миграция использует обычные `CREATE TABLE`, `CREATE TYPE`, `CREATE INDEX` и `ALTER TABLE ... ADD
CONSTRAINT`. При первом развёртывании они берут только краткие DDL-lock на создаваемые объекты; rewrite
или длительная блокировка существующих прикладных таблиц отсутствуют. Применение предполагает пустую
целевую схему без одноимённых объектов. Если в окружении уже есть созданные вне Prisma таблицы или enum,
сначала требуется отдельная сверка и baseline, а не принудительный запуск этой миграции.

SQL побайтно по содержимому после нормализации переводов строк сопоставлен с актуальным Prisma diff.
Реальная PostgreSQL не подключалась, миграция не применялась, `prisma db push`, reset, seed и
production-запросы не выполнялись. Применение остаётся отдельным release-шагом через
`prisma migrate deploy` после проверки целевого окружения.

## Пункт 33 — повторяемый seed каталога и настроек

Подготовлена явная Prisma seed-команда `tsx prisma/seed.ts`, зарегистрированная в
`prisma.config.ts`. Источником стартовых данных остаются текущие типизированные mock-контракты
каталога и профиля магазина; преобразование в DB-представление вынесено в `prisma/seed-data.ts` и
не меняет frontend-потребителей до интеграционного пункта 38.

Категории и товары адресуются по уникальному `slug`, основная конфигурация магазина — по ключу
`primary`, группы и значения опций — по составным стабильным ключам, изображения — по стабильному
`cloudinaryPublicId`, полученному из версионируемого mock-пути. Характеристики обновляются по
`(productId, label)`. Все известные записи создаются или обновляются через `upsert`; seed не содержит
`delete`, `deleteMany`, `TRUNCATE` или сверку с удалением отсутствующих записей, поэтому данные,
которых нет в стартовом наборе, сохраняются.

Seed выполняет каталог и настройки в одной интерактивной транзакции с увеличенным timeout. Для
первичного перехода локальные пути изображений записываются в существующее поле `secureUrl`, а
стабильный public id резервируется под последующую загрузку в Cloudinary. Отсутствующие в mock-модели
операционные поля получают явные стартовые значения: `stock = 10`, `isActive = true`, стиль
`Современный`; материал и размеры берутся из одноимённых характеристик с безопасным текстовым
fallback. Денежные значения передаются в Prisma decimal-строками с двумя знаками после запятой.

Чтобы настройки действительно сохраняли текущий `storeProfile`, модель `StoreSettings` расширена
полями `name`, `description`, `contacts`, `socials` и timestamps. Изменение классифицировано как
совместимое `schema + data`: миграция только добавляет столбцы, временные defaults обеспечивают
backfill возможной существующей записи, после чего прикладные defaults удаляются. `DROP` таблиц,
сужения типов и удаления строк нет; rollback выполняется forward-fix миграцией, поскольку удаление
заполненных столбцов было бы destructive.

Реальная PostgreSQL не подключалась, миграция и seed не применялись: запуск seed остаётся отдельным
явным действием оператора и запрещён для production. Проверка mapping покрывает полноту mock-каталога,
уникальность стабильных ключей, позиции дочерних записей и профиль `primary`.

## Пункт 35 — единый денежный контракт

В `src/shared/money.ts` определён единый `MoneyDto` с формой `{ amount: string; currency: "BYN" }`.
Канонический `amount` неотрицателен, не содержит ведущих нулей, всегда имеет два знака после точки и
ограничен десятью цифрами целой части в соответствии с `Decimal(12, 2)`. Общая Zod-схема переиспользуется
каталожным DTO вместо отдельного ослабленного регулярного выражения.

Mapper принимает Prisma-compatible Decimal-like значение через его точный `toFixed(2)` и возвращает
только прошедший общую схему JSON-safe объект. Временный вход `number` оставлен исключительно для
поэтапного перевода существующих mock/frontend-моделей; он не является серверным источником истины.
Обратное преобразование в `number` применяется только для отображения, а не для расчёта итогов.

Общий formatter локализует и `MoneyDto`, и legacy `number` в `ru-BY`/`BYN`, показывая до двух дробных
знаков. Существующие каталог, корзина, профиль и административные mock-интерфейсы переведены с локальных
экземпляров `Intl.NumberFormat` на этот formatter. Prisma-запросы и доменные mapper результатов остаются
объёмом пунктов 36–37; серверное вычисление заказа — последующих пунктов заказов.

## Пункт 37 — mapper результатов Prisma в публичные DTO

В server-областях `catalog` и `settings` добавлены отдельные доменные mapper-функции. Service больше
не возвращает Prisma-shaped records: категории, превью и детали товара, публичные настройки и cursor
пагинации преобразуются в соответствующие строгие DTO до выхода из server-only слоя.

Внутренний `BigInt` товара и cursor преобразуется в decimal-строку, даты — в ISO 8601 UTC, Prisma
`Decimal` — в общий `MoneyDto`. Группы и значения опций получают публичные идентификаторы из
стабильных `key`, а не DB id. Cloudinary public id, `createdAt`, остаток, флаг активности и другие
служебные поля не попадают в результат. JSON-колонки контактов и соцсетей настроек считаются
недоверенными и повторно проверяются через строгую Zod-схему с безопасными URL.

Mapper намеренно отклоняет товар без основного изображения и любую запись, нарушающую публичный
контракт, вместо выдачи частично валидного DTO. Изменение является query/contract-only: Prisma schema,
миграции и данные не менялись, реальная PostgreSQL не подключалась. UI и transport остаются объёмом
следующих пунктов плана.

В Prisma schema добавлены совместимые с официальным Prisma Adapter модели `User`, `Account`, `Session`
и `VerificationToken`. Auth identity использует отдельный строковый `cuid`, поскольку контракт adapter
оперирует строковым `userId`; доменные `BigInt`-идентификаторы каталога от этого не меняются.

Выбрана database session strategy: `Session` хранит уникальный случайный `sessionToken`, срок действия
как `timestamptz(3)` и обязательную ссылку на пользователя. `Account` содержит полный adapter-контракт
OAuth/OIDC и удаляется каскадно вместе с `User`; то же правило применяется к активным сессиям.
`VerificationToken` не связан FK с пользователем, потому что до подтверждения identifier может не
соответствовать существующей записи. Token уникален, а пара `identifier + token` является primary key.

Изменение классифицировано как совместимое `schema-only`: существующие модели и данные не меняются,
SQL-миграция и дополнительные поисковые индексы намеренно оставлены пункту 42. Обязательный уникальный
`email` добавлен как часть adapter-контракта; его серверная нормализация, а также поля `role`, `phone`,
`passwordHash` и lifecycle-поля пользователя относятся к пункту 41 и не добавлены преждевременно.
Prisma Adapter ещё не установлен и не подключён — это часть backend-интеграции следующих пунктов;
schema сверена с контрактом установленного Auth.js 5 и
официальной схемой adapter. Реальная PostgreSQL не подключалась, `db push`, migrate и seed не запускались.

## Пункт 41 — роли и credentials-поля пользователя

В Prisma schema добавлен enum `UserRole` со значениями `USER` и `ADMIN`; поле `User.role` получает
безопасное значение `USER` по умолчанию. Роль является server-managed атрибутом и не должна
приниматься из регистрации, формы профиля или другого клиентского payload.

В `User` добавлены nullable `phone` и `passwordHash`. Nullable hash поддерживает одновременно
Credentials identity и пользователей без локального пароля; открытый пароль в схеме отсутствует.
Телефон не является идентификатором входа и пока не получает unique-ограничение.

Единственным email-полем остаётся `User.email` с существующим unique-инвариантом. Его каноническое
значение формируется на каждой будущей server-side write-границе через `trim` и lowercase до записи
или поиска; отдельное дублирующее `normalizedEmail` не вводится. Prisma/PostgreSQL сами по себе не
приводят регистр, поэтому подключение Auth.js и Credentials в следующих пунктах обязано использовать
единую нормализацию и обрабатывать unique-конфликт.

Изменение классифицировано как совместимое `schema-only`: существующие строки при будущей миграции
получат `USER`, nullable-поля не требуют backfill, данные не удаляются и типы не сужаются. SQL-миграция
и индексы остаются пунктом 42; реальная PostgreSQL не подключалась, `db push` и migrate не запускались.

## Пункт 42 — миграция Auth.js и поисковые индексы

Создана версионируемая additive-миграция для enum `UserRole` и таблиц `User`, `Account`, `Session`,
`VerificationToken`. Миграция не изменяет существующие таблицы каталога и настроек, не требует
backfill и не содержит `DROP`, сужения типов или преобразования существующих строк.

Пути Auth.js закреплены индексами по фактическим lookup: unique `User.email`, составной primary key
`Account(provider, providerAccountId)`, unique `Session.sessionToken` и unique
`VerificationToken.token`. Для внешних ключей дополнительно добавлены `Account.userId` и
`Session.userId`, чтобы relation lookup и каскадное удаление пользователя не требовали полного
сканирования дочерних таблиц. Отдельные дублирующие индексы по `provider`, `identifier`, `expires` или
`role` не добавлены без связанного запроса.

Prisma schema успешно прошла validate/generate, а полный DDL, сгенерированный Prisma из schema,
подтвердил совпадение типов, ключей, индексов и FK с миграцией. Реальная PostgreSQL не была доступна,
поэтому миграция не применялась; перед общим или production deploy остаётся обязательным migration
job через direct `DATABASE_URL_UNPOOLED` с предварительным просмотром SQL.

## Пункт 43 — административная авторизация Auth.js

Auth.js 5 подключён через Credentials provider и route handler `/api/auth/[...nextauth]`. Вход
выделяет из Auth.js payload allowlist `email/password`, канонизирует email через `trim + lowercase`,
выбирает из PostgreSQL только необходимые поля и допускает исключительно пользователя с актуальной
ролью `ADMIN` и локальным `passwordHash`. Ответ при неверном email, пароле или роли одинаковый.

Credentials provider установленной версии Auth.js несовместим с database session strategy и при
такой конфигурации возвращает `UnsupportedStrategy`. Поэтому для первого административного входа
выбрана поддерживаемая JWT strategy с максимальным сроком 8 часов. JWT содержит только id и роль,
однако не является источником авторизации: общий server-only `requireAdmin()` повторно читает
пользователя из БД и проверяет текущую роль перед защищённой операцией. Это обеспечивает немедленный
запрет новых операций после снятия роли или удаления пользователя. Созданные ранее adapter-таблицы
остаются для будущих OAuth/database-сценариев и не используются для самодельного обхода Auth.js.

Пароли хешируются versioned salted `scrypt` (`N=16384`, `r=8`, `p=1`, 64-byte key, случайная
16-byte salt) средствами Node.js; сравнение выполняется constant-time, формат и параметры строго
проверяются до дорогостоящего вычисления. Создание первого администратора и запись этого hash
остаются отдельным пунктом 45; открытый пароль, hash и session token не добавляются в Git или логи.

## Пункт 44 — авторизация административных операций

Введён единый server-only wrapper `withAdminAuthorization()` для экспортируемых защищённых Route
Handlers, Server Actions и административных mutation entry points. Wrapper до вызова операции
выполняет `requireAdmin()`: получает Auth.js session, извлекает идентификатор пользователя и повторно
читает из PostgreSQL актуальные `id`, `email` и `role`. Отсутствующая session отклоняется отдельно от
пользователя без текущей роли `ADMIN`; снятие роли или удаление пользователя немедленно запрещает
следующую операцию независимо от значения роли в JWT.

Публичные схемы входа, регистрации, восстановления и изменения профиля переведены на строгие
allowlist-контракты. Неизвестные поля, включая `role` и `passwordHash`, отклоняются и не могут попасть
в будущую Prisma write-операцию через object spread или mass assignment. Роль остаётся исключительно
server-managed атрибутом; отдельное контролируемое создание первого администратора относится к
пункту 45.

На текущем этапе production CRUD Route Handlers и Server Actions ещё отсутствуют: Auth.js endpoint
является публичным transport входа, а административные операции товаров, изображений, настроек и
заказов появляются в следующих пунктах. Для них использование wrapper на каждой экспортируемой
серверной границе является обязательным, а middleware и клиентский preview-gate не считаются
авторизацией.

## Пункт 45 — создание первого администратора

Реализована отдельная server-only CLI-команда `npm run admin:create-first`. Она подключается только через
direct `DATABASE_URL_UNPOOLED`, валидирует и нормализует `FIRST_ADMIN_EMAIL`, требует пароль длиной
12–128 символов из `FIRST_ADMIN_PASSWORD` и принимает optional `FIRST_ADMIN_NAME`. Значения не передаются
CLI-аргументами, не добавляются в `.env.example`, seed, миграцию или Git и не выводятся в сообщения об
ошибках. После выполнения оператор обязан удалить одноразовые job secrets и проверить вход.

Внутри одной транзакции команда берёт фиксированный PostgreSQL transaction-level advisory lock, проверяет
отсутствие любой записи с ролью `ADMIN`, затем проверяет уникального владельца нормализованного email и
создаёт пользователя только с server-assigned ролью `ADMIN` и salted `scrypt` hash. Lock сериализует
параллельные bootstrap-запуски. Повторный запуск при существующем администраторе является no-op; совпадение
email с обычным пользователем приводит к отказу без автоматического повышения привилегий.

Команда выводит только обезличенный итог и не раскрывает connection string, email, пароль или hash.
Фактический запуск против PostgreSQL и создание реального администратора в рамках пункта не выполнялись.
Отдельная audit-модель пока отсутствует; минимальный execution audit должен обеспечиваться защищённым job
платформы до появления доменного audit log.

## Пункт 46 — административный CRUD каталога

Реализован server-only административный контракт для категорий, товаров, характеристик, групп опций,
значений опций и metadata изображений. Публичная граница каждой операции сначала повторно проверяет
текущую Auth.js session и актуальную роль `ADMIN`, а затем передаёт во внутренний сервис только ID и
входной DTO. Служебная инъекция PrismaClient остаётся внутренней и не входит в защищённый контракт.

Все create/update payload описаны строгими Zod allowlist-схемами: неизвестные поля отклоняются, цена
принимается точной decimal-строкой, даты — ISO 8601 со смещением, ID — положительной decimal-строкой,
позиции и длины полей ограничены. Валюта `BYN` назначается сервером. Prisma `data` формируется только
из прошедших проверку полей; внутренние ID, timestamps и currency нельзя назначить клиентским payload.

Существование категории, товара или группы опций проверяется в той же транзакции, где создаётся
зависимая запись. Удаление непустой категории запрещено до переноса или удаления её товаров; удаление
товара использует существующие каскадные FK для его характеристик, опций и metadata изображений.
Фактическое удаление бинарного объекта Cloudinary намеренно не выполняется: согласованный lifecycle
внешнего ресурса относится к пункту 47. Схема БД и миграции не менялись; live PostgreSQL не вызывалась.

## Пункт 47 — подписанные загрузки и lifecycle Cloudinary

Добавлен server-only адаптер установленного Cloudinary SDK. Route Handler
`POST /api/admin/uploads/signature` принимает только ID существующего товара и через защищённую
границу повторно проверяет Auth.js session и актуальную роль `ADMIN`. Сервер генерирует уникальный
`public_id` внутри `virtual-space/products/<productId>/`, подписывает короткоживущий timestamp,
allowlist raster-форматов и ограничивающую размеры transformation; API secret остаётся только на
сервере.

Результат прямой загрузки не считается доверенным metadata. Перед созданием или заменой
`ProductImage` backend получает ресурс через Cloudinary Admin API и проверяет точный `public_id`, тип
`image`, HTTPS URL, формат, размер до 10 MiB и измерения до 4096×4096. В БД записываются URL и public ID
из ответа Cloudinary, а не из клиентского payload; alt, position и идентификаторы проходят строгую
Zod allowlist-валидацию.

При неуспешной фиксации новой записи новый ресурс удаляется best-effort. При замене сначала
транзакционно переключается metadata, затем идемпотентно удаляется старый ресурс. Отдельное удаление
изображения и каскадное удаление товара сначала убирают metadata из PostgreSQL, затем очищают
Cloudinary; сбой внешней очистки возвращается как `cleanupPending`, не восстанавливая в БД ссылку на
устаревший ресурс. Гарантированная фоновая очистка потребует durable outbox/job и остаётся осознанным
остаточным ограничением до появления такой инфраструктуры. Компенсация после DB-конфликта повторно
проверяет `cloudinaryPublicId` в PostgreSQL и не удаляет ресурс, который успела зафиксировать
конкурентная операция. Prisma schema и миграции не менялись.

## Пункт 48 — защищённое управление настройками магазина

Созданы две server-only административные операции: чтение основной записи `StoreSettings` и её
полное обновление. Обе публичные границы используют `withAdminAuthorization()`, поэтому до Prisma
повторно проверяются Auth.js session и актуальная роль `ADMIN` в PostgreSQL. Отсутствующая основная
запись при чтении возвращается как отдельная доменная ошибка; автоматическое создание второй записи
или выбор клиентского ключа не допускаются.

Для update переиспользуется строгий публичный DTO настроек: неизвестные поля отклоняются, размеры
строк и массивов ограничены, контакты принимают только `https`, `mailto` и `tel`, а социальные ссылки
только `https`. Prisma write собирается явным allowlist из `name`, `description`, `contacts` и
`socials`; ключ `primary`, ID и timestamps остаются server-managed. Возвращаемое значение проходит
явный select и повторную Zod-валидацию JSON-полей. Prisma schema, миграции и данные не менялись;
подключение preview-формы `/admin/settings` остаётся пункту 49.

## Пункт 49 — подключение административного UI к Auth.js и PostgreSQL

Маршруты `/admin`, `/admin/products` и `/admin/settings` переведены с preview-gate на server-side
проверку Auth.js session и актуальной роли `ADMIN`. Credentials-форма вызывает Auth.js, выход

Обзор рассчитывает показатели каталога через Prisma. Товары и настройки получают начальные DTO в
Server Components и изменяются через Server Actions, которые повторно используют защищённые

компоненты удалены. Экран заказов и его mock transport намеренно не менялись: модели и backend
заказов относятся к следующим пунктам плана.

В UI товаров подключены чтение, создание, редактирование и удаление основных полей товара, а также
галерея: клиентская проверка файлов и preview, подписанная прямая загрузка в Cloudinary, серверная
проверка загруженного ресурса и удаление сохранённых изображений через lifecycle пункта 47. Новый
товар до успешной фиксации обязательной галереи создаётся неактивным и публикуется отдельной
защищённой мутацией только после загрузки; при замене сначала фиксируются новые ресурсы и лишь затем
удаляются выбранные старые изображения, чтобы сбой загрузки не приводил к потере прежней галереи.

## Пункт 51 — основные модели заказа

В Prisma schema добавлен `Order` с внутренним `BigInt` id и независимым уникальным `publicNumber`,
nullable-связью с `User`, обязательным снимком имени, телефона и email покупателя, optional
комментарием, валютой `BYN`, точным итогом `Decimal(12, 2)`, статусом и timezone-aware
`createdAt`/`updatedAt`. Удаление пользователя отвязывает заказ через `SetNull`, не уничтожая
контактный снимок и хозяйственную историю.

Созданы связанные валидные каркасы `OrderItem` и `OrderStatusHistory` с собственными `BigInt` id,
обязательным `orderId` и timestamps. Обе связи используют `onDelete: Restrict`, поэтому заказ с

Обязательные снимки товарной позиции, nullable-ссылка на исходный товар, enum переходов и optional

До пункта 54 `Order.status` является внутренней строкой с default `NEW`; до миграции пункта 57 она
будет заменена закрытым enum `OrderStatus`. Это совместимый `schema-only` expand-шаг: существующие
таблицы и данные не изменялись, SQL-миграция, `db push`, seed и подключение к PostgreSQL не
выполнялись. Индексы путей чтения, PostgreSQL CHECK-ограничения и единая миграция остаются пунктам
55–57. Публичные DTO, backend создания заказа и UI не менялись.
