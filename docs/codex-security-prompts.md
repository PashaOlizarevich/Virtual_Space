# Промпты Codex Security для плана Virtual Space

Документ задаёт контрольные точки применения Codex Security при выполнении
`docs/implementation-plan.md`. Плагин используется после завершения логического блока, а не после
каждого небольшого пункта.

## Быстрый пример запроса

После завершения блока скопировать запрос и заменить диапазон пунктов на нужную контрольную точку:

```text
Выполни аудит через Codex Security по промпту из docs/codex-security-prompts.md для пунктов 23–25.
Код, документацию, схему, миграции и данные не изменяй. Сначала представь read-only отчёт с
подтверждёнными findings, уровнем критичности, точными файлами и строками, достижимым сценарием риска
и минимальным исправлением.
```

Если findings подтверждены и их разрешено исправить, отправить следующий запрос:

```text
Используя Codex Security, исправь подтверждённые findings из последнего аудита пунктов 23–25.
Не расширяй область задачи. Добавь разрешённые regression-тесты, повтори проверку исправлений и
запусти проверки проекта. Существующие E2E и файлы tests/e2e/** не изменяй без моего отдельного
явного разрешения.
```

## Общий порядок

1. Убедиться, что отмеченный блок плана реализован и прошёл предусмотренные для него проверки.
2. Отправить read-only промпт соответствующей контрольной точки. На этом шаге не разрешать изменение
   кода, схемы, миграций, конфигурации и данных.
3. Рассмотреть findings. Finding должен содержать точное место, достижимый сценарий эксплуатации или
   нарушения целостности, последствия, уровень критичности и минимальное исправление.
4. Отдельным запросом разрешить исправление подтверждённых findings.
5. После исправления запустить релевантные unit- и integration-тесты, `prisma validate`,
   `prisma generate`, ESLint, TypeScript и production build. E2E создавать или изменять только после
   отдельного явного разрешения согласно правилам проекта.

Codex Security дополняет обязательные правила `.codex/rules/security.md` и локальный
`security-review`, но не заменяет серверную валидацию, тесты, review SQL-миграций и проверку
архитектуры. Если плагин недоступен, исполнитель должен явно сообщить об этом и не утверждать, что
аудит через Codex Security выполнен.

## Универсальный промпт исправления

Использовать только после рассмотрения read-only отчёта:

```text
Исправь подтверждённые findings из последнего аудита Codex Security в рамках проверенного блока
плана. Не расширяй область задачи и не меняй архитектуру без необходимости. Для каждого исправления
добавь минимальный regression-тест, если это разрешено правилами проекта; существующие E2E и файлы
tests/e2e/** не изменяй без моего отдельного явного разрешения. Не выполняй destructive-миграции,
не изменяй production-данные и не читай значения секретов. После исправлений повтори Codex Security
review затронутого кода и запусти все проверки, предусмотренные пунктом 85. В отчёте сопоставь каждый
finding с исправлением, тестом и результатом повторной проверки.
```

## Контрольная точка после пунктов 23–25

Цель: проверить решения первого DB-релиза до создания схемы и runtime-кода.

```text
Используй Codex Security и проведи read-only аудит решений, зафиксированных при выполнении пунктов
23–25 docs/implementation-plan.md. Код и документацию не изменяй. Проверь модель ролей и границы
первого этапа Auth.js, представление денег и товарных опций, правила хранения и анонимизации данных,
onDelete-последствия, доступ к секретам, bootstrap первого администратора и разделение local,
preview и production. Не читай значения .env, credentials или production-данные. Для каждого finding
укажи severity, точное место в документации, достижимый сценарий риска, последствия и минимальную
рекомендацию. Отдели подтверждённые проблемы от вопросов, требующих юридического или продуктового
решения.
```

## Контрольная точка после пунктов 26–39

Цель: проверить каталог, Prisma-схему, миграции, seed, запросы и публичные DTO.

```text
Используй Codex Security и проведи read-only аудит реализации пунктов 26–39
docs/implementation-plan.md. Ничего не изменяй и не применяй миграции. Сопоставь Prisma schema с
фактическим SQL миграций; проверь неожиданные DROP, NOT NULL без backfill, сужение типов, FK,
onDelete, unique и CHECK constraints, Decimal и даты, повторяемость seed, mass assignment, выборку
неопубликованных или внутренних полей, сериализацию DTO, server-only границы PrismaClient и
неограниченные/N+1-запросы. Finding подтверждай конкретным сценарием потери данных, обхода правил,
утечки или несовместимого deploy. Представь findings по severity с точными файлами и строками;
код, БД и данные не изменяй.
```

```text
Используй Codex Security и проведи read-only аудит реализации пунктов 40–50
docs/implementation-plan.md. Код не изменяй. Проверь конфигурацию Auth.js и adapter, хранение и
проверку паролей, cookies и сессии, CSRF, session fixation, server-side проверку роли ADMIN на каждом

Zod-валидацию, bootstrap администратора, подписанную загрузку Cloudinary, ограничения типа и размера

секретов. Для каждого finding укажи severity, точное место, достижимый сценарий эксплуатации и
минимальное исправление. Не выводи значения секретов и не изменяй данные.
```

## Контрольная точка после пунктов 51–67

Цель: проверить оформление заказа, снимки данных, остатки, статусы и Telegram.

```text
Используй Codex Security и проведи read-only аудит реализации пунктов 51–67
docs/implementation-plan.md. Код и БД не изменяй. Проверь недоверенную гостевую корзину, повторное
получение цены и доступности на сервере, канонизацию выбранных опций, контролируемый конфликт цены,
точность Decimal, снимки OrderItem, атомарность создания заказа, гонки за последний остаток,
rollback, идемпотентность повторной отправки, допустимые переходы статусов, административную роль,
владение заказом гостя или пользователя, публичные идентификаторы и утечки данных покупателя.
Отдельно проверь, что Telegram вызывается только после commit, не получает лишние персональные данные
и не влияет на сохранение заказа при сбое. Findings представь по severity с точным сценарием и
минимальным исправлением.
```

## Финальная контрольная точка после пункта 84

Цель: проверить приложение целиком перед production и найти проблемы на границах модулей.

```text
Используй Codex Security для полного read-only аудита Virtual Space после выполнения пункта 84 и
перед production. Ничего не изменяй. Проверь всю цепочку: публичный каталог, Auth.js, роли и сессии,
административные операции, Cloudinary, пользовательские данные, гостевую и серверную корзины,
оформление заказа, Decimal, транзакции и остатки, статусы, Telegram, Prisma schema и SQL-миграции,
DTO, ошибки, логирование, rate limits, секреты, зависимости и конфигурацию deploy. Ищи проблемы на
стыках модулей и не повторяй уже закрытые findings без нового доказательства. Представь executive
summary, findings по severity с файлами и строками, достижимый сценарий эксплуатации, последствия,
минимальное исправление, необходимые regression-тесты и остаточный риск. Отдельно перечисли
неподтверждённые предположения и проверки, требующие внешней инфраструктуры. Не читай секреты, не
подключайся к production и не выполняй destructive-действия.
```

После исправления подтверждённых findings повторить финальный read-only аудит тем же промптом и
сопоставить результат с предыдущим отчётом.
