# План реализации поискового mega-menu и фильтров каталога

## Как использовать этот план

Добавьте файл в чат Codex и дайте команду вида:

```text
Выполни пункт 7 из Плана_на_поисковое_меню.md
```

AI-агент должен выполнить только указанный пункт. Следующие пункты нельзя выполнять автоматически,
кроме минимальных связанных изменений, без которых текущий пункт не собирается или не работает.

Перед выполнением любого пункта AI-агент обязан:

- Прочитать `AGENTS.md`, применимые `.codex/rules/**`, `docs/progress.md` и указанные в пункте
  проектные документы.
- Проверить фактический код, версии, Git status, текущую ветку и выполнение предыдущих зависимостей.
- Если обязательный предыдущий пункт не реализован, остановиться и назвать зависимость, а не
  выполнять её скрытно.
- Использовать указанные skills и существующие архитектуру, зависимости, UI-компоненты и тестовые
  инструменты проекта.
- Изменить только относящиеся к пункту файлы, сохранить пользовательские изменения и не
  устанавливать зависимости без разрешения.
- Выполнить применимые проверки, просмотреть итоговый diff, обновить требуемую документацию и
  передать отчёт о результате, файлах, проверках, ограничениях, ветке и локальных коммитах.
- Остановиться после отчёта. Не выполнять push, merge, rebase, создание PR, Preview/Production
  deployment и другие внешние действия без отдельного прямого разрешения пользователя.

Для feature-кода применять `create-feature`; для API и server contracts — `api-development`; для
React/UI — `create-component`, `build-web-apps:react-best-practices` и
`build-web-apps:shadcn`; для Prisma, migration, seed и backfill — `database-change`; после
чувствительных блоков — read-only `security-review`. Перед любой работой с тестами обязательно
читать `.codex/rules/testing.md`.

## Неизменяемые требования функции

- Иконка поиска открывает одно общее mega-menu на базе доступного `<dialog>`.
- При каждом открытии первым показывается общий экран `Обзор`/`Все`.
- Из него внутри того же dialog открываются подпункты `Категории`, `Цена`, `Габариты`,
  `Цвета`, `Материалы`, `Наличие и новинки`, `Сортировка`.
- Кнопка `Назад` возвращает в `Обзор`; вложенные dialog не создаются.
- Desktop использует список подпунктов слева и активную область справа. Mobile показывает сначала
  общий экран, затем один выбранный подпункт.
- Header и `/catalog` управляют одним смонтированным экземпляром mega-menu с уникальным ID.
- Применённое состояние хранится в URL; локальный state существует только как draft открытого меню.
- Внутри одной группы фильтров действует OR, между разными группами — AND.
- Поиск и фильтрация выполняются в PostgreSQL до пагинации.
- Существующее mega-menu `Каталог` остаётся отдельным; одновременно открывается только одна панель.
- Не добавлять внешний search service, AI-рекомендации, autocomplete на каждый символ,
  `ProductVariant`, отдельные SKU/цены/остатки по цветам и новые UI-зависимости.

## План по пунктам

1. **[Подготовка, использовать create-feature]** Изучить фактические Header, `HeaderSearch`,
   `CatalogMenu`, mobile navigation, `/catalog`, `CatalogQueryGridView`, catalog
   service/query/DTO/mapper, Prisma schema, seed, production bootstrap, admin CRUD, связанные тесты
   и стили. Подтвердить текущие версии и ограничения: `search` пока не обрабатывается, каталог
   получает максимум 100 товаров и пагинирует их на клиенте. Выполнить baseline-проверки, создать по
   `docs/git-flow.md` отдельную feature-ветку и не менять пользовательские файлы.

2. **[URL-контракт, использовать api-development]** Создать
   `src/modules/catalog/search-params.ts` с Zod parsing/normalization/serialization и тестами.
   Поддержать `search`, повторяющиеся `category/color/material`, диапазоны цены и трёх размеров,
   `inStock=1`, `isNew=1`, allowlisted `sort` и положительный `page`. Ограничить длину текста,
   число повторов и диапазоны; дедуплицировать значения; пустые и неизвестные значения безопасно
   исключать; `min > max` возвращать как контролируемую field error; при изменении фильтра удалять
   `page`.

3. **[Текстовый поиск, использовать api-development]** Реализовать общий builder Prisma `where`
   для `isActive: true` и case-insensitive поиска по `name`, `description`, `category.name`,
   legacy `material` и `style`. Поиск применять до пагинации, выбирать только необходимые поля,
   не возвращать Prisma-модели, BigInt, Decimal и внутренние детали. Добавить server-тесты поиска,
   пустого запроса и обязательной фильтрации неактивных товаров.

4. **[Серверная выдача, использовать api-development]** Добавить для `/catalog` paged
   service/DTO с `products`, `categories`, `total`, `page`, `pageCount`, `pageSize=12` и
   нормализованными параметрами. Page query и count должны использовать один `where`.
   `recommended` пока сортирует как `createdAt desc, id desc`; это не называть релевантностью.
   Существующий cursor-контракт главной и страниц категорий не ломать.

5. **[Страница каталога, использовать create-component]** Перевести
   `src/app/(store)/catalog/page.tsx` и `CatalogQueryGridView` с загрузки первых 100 товаров и
   клиентского `slice` на серверную пагинацию по 12 записей. Использовать фактический Next.js 16
   API `searchParams` и навигацию Next.js вместо ручного history как источника серверных данных,
   сохранять остальные query-параметры и Back/Forward.

6. **[Результаты поиска, использовать create-component]** Для активного запроса скрывать
   редакционную мозаику категорий и показывать query, total, пагинацию, очистку текста,
   loading/updating/error и отдельное состояние `Ничего не найдено`. Пустой результат поиска не
   называть пустым каталогом. Добавить/обновить относящиеся component/integration-тесты, сохранив
   текущие сценарии карточек.

7. **[Контроль серверного поиска]** Запустить targeted и полный Jest, Prettier, ESLint, typecheck и
   production build; проверить главную, страницы категорий, товар, корзину и checkout. Выполнить
   read-only security review parser/query/DTO. Исправить только подтверждённые findings, обновить
   применимую документацию и создать локальный savepoint-коммит рабочего текстового поиска.

8. **[Поисковое mega-menu, использовать create-component]** Заменить компактное раскрытие
   `HeaderSearch` на trigger одного portal/dialog. Доменную разметку разместить в catalog module, а
   Header оставить layout-композицией. На `/catalog` добавить trigger того же экземпляра, не
   монтировать второй dialog и не дублировать ID или бизнес-логику фильтров.

9. **[Общий экран и подпункты, использовать create-component]** Реализовать state machine
   `overview -> section -> overview`. При каждом открытии сбрасывать активную секцию в
   `overview`, загружать draft из текущего URL, фокусировать поиск и показывать query, summary,
   chips, доступные подпункты и действия. Переход в подпункт меняет рабочую область того же dialog,
   `Назад` возвращает в обзор, закрытие без применения отбрасывает draft, а применение создаёт
   канонический `/catalog?...` без `page`.

10. **[Категории]** Передавать в mega-menu безопасные `CategoryDto` из PostgreSQL, не создавать
    третий статический список. Добавить повторяющийся `category` в service/query как
    `category.slug in [...]`, реализовать доступный множественный выбор, chips и восстановление из
    URL; неизвестные или недоступные slug безопасно нормализовать.

11. **[Взаимодействие панелей]** Координировать Search, Catalog, mobile navigation и cart dialog:
    перед открытием новой панели закрывать уже открытую, не допускать нескольких overlay/focus trap
    и возвращать focus фактическому trigger. Проверить закрытие кнопкой, Escape и overlay, блокировку
    прокрутки фона и сохранение URL при отмене.

12. **[Адаптивность и доступность mega-menu]** Реализовать desktop-композицию с навигацией слева и
    рабочей областью справа, а на tablet/mobile — один экран за раз с явными `Назад` и
    `Закрыть`. Соблюсти `docs/DESIGN.md`, focus trap, accessible title, fieldset/legend,
    связанные label/error, target 44x44px, `focus-visible`, WCAG 2.2 AA,
    `prefers-reduced-motion` и отсутствие overflow Header.

13. **[Контроль mega-menu]** Покрыть overview, все доступные переходы, draft/apply/cancel,
    категории, focus return и взаимоисключение панелей component/integration-тестами. Выполнить
    browser-проверку mobile/tablet/desktop, Console и Network, затем полный набор проверок,
    документацию и локальный savepoint-коммит законченного mega-menu с текстом и категориями.

14. **[Фильтры существующих полей, использовать api-development]** Добавить в parser/service/query
    цену `priceMin/priceMax`, `inStock=1` как `stock > 0`, `isNew=1` как включительное
    `newFrom <= now <= newUntil` с передаваемым из service временем и сортировки
    `recommended`, `newest`, `price-asc`, `price-desc`. Для каждого порядка использовать
    стабильный ID tie-breaker, для `newest` — `nulls last`.

15. **[UI существующих фильтров, использовать create-component]** Включить подпункты `Цена`,
    `Наличие и новинки`, `Сортировка` только после готовности backend. Использовать числовые
    поля, checkbox и select без новой зависимости. Добавить удаление одного chip,
    `Сбросить фильтры` с сохранением search и `Очистить поиск` для полного сброса; каждое
    изменение сбрасывает страницу.

16. **[Count endpoint, использовать api-development]** Если интерфейсу нужна подпись
    `Показать N товаров`, создать read-only `/api/catalog/search-count`, переиспользовать общий
    parser/where/service и возвращать только `{ count }`. Ограничить ввод и безопасные ошибки,
    использовать debounce и AbortController; ошибка endpoint или отсутствие JavaScript не должны
    ломать обычную GET-навигацию к результатам.

17. **[Контроль фильтров]** Покрыть цену и invalid range, stock, границы новинки, сортировки,
    AND/OR, reset, Back/Forward, page reset и совпадение page total/count endpoint. Выполнить
    security review публичной границы, полный набор проверок, документацию и локальный
    savepoint-коммит фильтров по существующим колонкам.

18. **[Габариты: expand, использовать database-change]** Добавить nullable
    `widthCm/depthCm/heightCm` как Prisma Decimal/PostgreSQL `numeric(8,2)` и CHECK `>= 0`,
    сохранив legacy `dimensions`. Создать новую timestamped migration, вручную проверить SQL на
    DROP, NOT NULL, table rewrite, блокировки и совместимость со старым приложением; выполнить Prisma
    и regression-проверки.

19. **[Габариты: admin и новые данные]** Расширить admin schemas/DTO/service и форму товара
    необязательными полями `Ширина/Глубина/Высота, см`; сохранить строку `Размеры` для
    отображения. Подготовить явную mapping-таблицу известных seed slug и обновить seed/bootstrap,
    чтобы новые товары сразу получали structured dimensions. Не использовать общий runtime-regex.

20. **[Габариты: backfill, использовать database-change]** Создать idempotent script с явным
    target `preview|production`, который обновляет только известные slug и пустые structured fields,
    сохраняет значения администратора и выводит только безопасные counts. Учесть `W x D x H`,
    `W x L`, `diameter x H`; неоднозначные значения оставлять nullable. Подключить script к
    production workflow после migration/bootstrap сначала для Preview, затем после approval для
    Production; не запускать общий production seed.

21. **[Габариты: публичный фильтр]** Только после подтверждённого backfill добавить ranges трёх
    размеров в parser, Prisma query, count endpoint и подпункт `Габариты`. Товар с `null` по
    активной оси не считать совпадением. Покрыть каждую ось, nullable records, комбинации с другими
    фильтрами, chips и invalid ranges.

22. **[Контроль габаритов]** Выполнить отдельные совместимые релизы
    `schema expand -> Preview/Production backfill -> enable filter`; не объединять их в один
    опасный rollout. На каждой границе выполнить database-change проверки, security review, полный
    набор тестов, документацию и локальный savepoint-коммит. Не применять migration или backfill к
    внешней среде без отдельного разрешения пользователя.

23. **[Таксономии: expand, использовать database-change]** Добавить `ColorFamily` и
    `CatalogMaterial` со стабильными `slug/name/position/isActive`, явные
    `ProductColorFamily` и `ProductCatalogMaterial`, unique product/facet и необходимые обратные
    индексы. Создать и проверить additive migration, не удалять legacy `Product.material` и
    `ProductOptionGroup/ProductOption`.

24. **[Таксономии: доменные правила]** Создать базовые цвета `light`, `beige`, `gray`,
    `black`, `brown`, `green`, `blue`, `other` с русскими labels. Зафиксировать, что
    фильтруемый цвет означает представленность товара в цветовом семействе и не создаёт variant,
    SKU, цену или отдельный остаток. В URL использовать только стабильные taxonomy slug, не
    произвольные legacy labels.

25. **[Таксономии: admin, использовать api-development и create-component]** Добавить защищённые
    admin schemas/DTO/services/actions для создания, переименования, упорядочивания и деактивации
    taxonomy values и назначения товару нескольких цветов/материалов. Проверять Auth.js role
    `ADMIN`, существование relation IDs и mass assignment; запрещать физическое удаление
    используемого значения. Добавить доступный UI без новой зависимости.

26. **[Таксономии: seed и backfill, использовать database-change]** Обновить повторяемые
    seed/bootstrap для новых товаров и создать явный idempotent mapping известных product slug.
    Материал сопоставлять с известными данными, цвет — с известной option group `color`;
    неоднозначный цвет назначать `other` только явно. Backfill добавляет только отсутствующие
    relations, сохраняет operator assignments, выводит безопасные counts и проходит Preview до
    Production.

27. **[Таксономии: публичные фильтры]** После подтверждённого backfill включить повторяющиеся
    `color/material` в parser, Prisma relation filters, total/count и подпункты mega-menu.
    Реализовать OR внутри color, OR внутри material и AND с остальными группами; добавить labels,
    chips, reset и восстановление URL.

28. **[Контроль таксономий]** Проверить migration/FK/constraints/indexes, admin authorization и
    delete conflict, seed/backfill idempotency, неизвестные/deactivated slug, OR/AND и total/count
    parity. Выполнить security review, полный набор проверок, документацию и раздельные локальные
    коммиты `expand -> backfill -> enable`; внешние релизы выполнять только после разрешения.

29. **[Финальная UI-интеграция, использовать create-component]** Завершить общий экран mega-menu и
    toolbar `/catalog`: все реализованные подпункты, query, summary, chips,
    `Показать N товаров`, оба сброса, total, sorting и состояния loading/updating/error/empty.
    Повторно проверить desktop/mobile композицию, keyboard flow, focus, aria-live/aria-busy,
    контраст, reduced motion, overlay и отсутствие дублирующего dialog.

30. **[Производительность и финальная безопасность]** Проверить bounded queries, отсутствие N+1,
    лишних `include` и сериализации. Выполнить `EXPLAIN` основных filter/sort запросов на
    репрезентативной непроизводственной БД; индексы добавлять только по подтверждённому query path.
    Не добавлять full-text index заранее: измеренную проблему `contains` вынести в отдельную
    `database-change` задачу. Выполнить финальный read-only security review.

31. **[Финальная проверка и документация]** Запустить Prettier, Prisma validate/generate и migration
    history для DB-изменений, lint, typecheck, targeted/full Jest, production build и разрешённый
    E2E. В рамках исходного задания разрешён ровно один относящийся сценарий в существующем
    `tests/e2e/catalog.spec.ts`: Header -> Обзор -> запрос -> подпункты/фильтры -> URL/result ->
    Back/Forward -> chip reset -> полный сброс; другие E2E-файлы не менять без разрешения. Обновить
    только фактически затронутые `ProductTour`, API overview, architecture, migration/production
    docs и одну итоговую запись `docs/progress.md`.

32. **[Финальный release — только после отдельного разрешения]** Проверить diff, секреты,
    пользовательские изменения, CI и commit SHA; слить законченный блок в `main`, запустить
    `.github/workflows/production-release.yml` для полного SHA, дождаться Preview
    migration/bootstrap/backfill и smoke-проверки, получить approval Production и развернуть тот же
    SHA. Read-only проверить `https://virtual-space-tau.vercel.app`. При дефекте выпускать
    code-fix или новую forward-fix migration; не редактировать применённый SQL, не выполнять
    `prisma db push`, reset или слепой rollback.

## Готовность всей функции

Функция завершена только когда Header открывает единое mega-menu с начальным `Обзором`, каждый
подпункт работает внутри него, поиск и все фильтры выполняются в PostgreSQL до пагинации, URL
полностью восстанавливает состояние, admin поддерживает structured dimensions и таксономии,
desktop/mobile интерфейсы доступны, существующие каталог, товар, корзина и checkout не сломаны, а
все проверки и разрешённый Preview/Production rollout успешно завершены.
