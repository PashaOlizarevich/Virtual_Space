# Архитектура интернет-магазина мебели Virtual Space

## 1. Статус документа

Этот файл — основной источник архитектурных правил проекта. При расхождении с примерами кода новый код следует приводить к правилам этого документа либо сначала явно менять архитектурное решение здесь.

Документ основан на `TermsOfReference.md` и `TechnologyStack.md`. Целевая архитектура описывает новый интернет-магазин; существующий каталог `HomeWork` является отдельным финансовым приложением и не определяет структуру магазина.

### Текущее и целевое состояние

Документ одновременно фиксирует реализованный frontend, подключённый публичный DB-срез и целевую production-архитектуру. Обозначения в структуре проекта:

- `[есть]` — подтверждено фактическим кодом и доступно для переиспользования;
- `[временно]` — рабочая реализация текущего этапа, которую предстоит заменить без закрепления её как production-паттерна;
- `[цель]` — принятое архитектурное решение, которое создаётся только при реализации соответствующего сценария;
- `[этап N]` — отложенная возможность из плана продукта.

| Область          | Текущее состояние                                                 | Целевое состояние                                                                 |
| ---------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Каталог и товары | Prisma/PostgreSQL через server-only query/service и публичные DTO | Тот же источник; mock остаётся только seed/preview-инфраструктурой                |
| Категории        | Явные страницы категорий с выборками из PostgreSQL                | Динамический маршрут только при достаточном количестве однотипных категорий       |
| Изображения      | Оптимизированные локальные файлы в `public/images`                | Cloudinary для управляемых товарных изображений, метаданные в PostgreSQL          |
| Корзина          | Zustand, localStorage и mock-сверка                               | Zustand для гостевого UX и обязательная серверная сверка цены/доступности         |
| Избранное        | Zustand и localStorage со списком ID товаров                      | Гостевой Zustand плюс PostgreSQL-список пользователя с объединением после входа   |
| Авторизация      | Preview-сессии пользователя и администратора в sessionStorage     | Auth.js, серверная сессия и проверка роли на каждой защищённой операции           |
| Админка          | Клиентские preview-gates и mock transport                         | Защищённые Server Actions/Route Handlers и серверные сервисы                      |
| Заказы           | Валидация формы и mock submit                                     | Транзакционный order service, Prisma и уведомление Telegram после commit          |
| API и интеграции | Production endpoints и адаптеры не созданы                        | Route Handlers/Server Actions, Cloudinary и Telegram по соответствующим сценариям |

После архитектурно значимой реализации соответствующая позиция переводится из `[цель]` в `[есть]`, а заменённая временная реализация удаляется из дерева. Косметические изменения UI, новые товары и локальные стили сами по себе статусы архитектуры не меняют.

## 2. Выбранный подход

### Решение: модульный монолит на Next.js

Витрина, административная панель и backend размещаются в одном приложении Next.js с App Router. Приложение развёртывается как одна единица, использует одну PostgreSQL и внешнее хранилище изображений Cloudinary.

```text
Браузер
  │
  ├── Server Components / HTML ──┐
  ├── Server Actions ────────────┼──> сервер Next.js ──> модули ──> Prisma ──> PostgreSQL
  └── HTTP /api/* ───────────────┘                         │
                                                          ├──> Cloudinary
                                                          └──> Telegram Bot API
```

Это оптимальный вариант для текущего MVP: frontend и backend используют один TypeScript-проект, общие схемы и модули; не нужны отдельный API-репозиторий, CORS, дублирование типов и независимая эксплуатация двух приложений.

Краткое сравнение:

| Вариант                      | Плюсы                                                                                       | Минусы                                               | Решение            |
| ---------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------ |
| Модульный монолит Next.js    | Простая разработка и поставка, серверный рендеринг, общие типы, достаточные границы модулей | Требует дисциплины импортов                          | **Выбран**         |
| Отдельные frontend и backend | Независимое масштабирование и релизы                                                        | Два проекта, CORS, контракт и инфраструктура сложнее | Не оправдан сейчас |
| Микросервисы                 | Независимость крупных доменов                                                               | Высокая операционная и транзакционная сложность      | Не применять       |

Архитектура не использует Redis, очереди, repository-класс над Prisma, event bus, CQRS или микросервисы. Их можно вводить только для измеренной проблемы, которой нет в MVP.

## 3. Технологические границы

Используются в текущем коде:

- Next.js App Router, React и TypeScript — UI, маршрутизация и серверное приложение.
- Tailwind CSS, структура shadcn/ui и Lucide React — визуальный слой и доступные примитивы. Radix UI не считается используемой технологией, пока конкретный компонент и зависимость не добавлены в проект.
- Framer Motion — только осмысленные клиентские анимации.
- Zustand — локальное клиентское состояние корзины гостя, избранного и UI; не серверный кеш.
- TanStack Query — клиентские запросы, которым действительно нужны повторная загрузка, мутации или кеш в браузере. Серверные страницы не обязаны дублировать данные в Query.
- React Hook Form и Zod — формы и входные контракты.
- Jest и Playwright — unit/integration и end-to-end тесты согласно выбранному стеку.

Выбраны для production/backend-этапа, но не считаются подключённой функциональностью только из-за наличия пакета:

- Prisma — единственная точка обычного доступа приложения к PostgreSQL.
- Auth.js — сессии и идентификация пользователей/администраторов.
- Cloudinary — бинарные изображения; в БД находятся метаданные и идентификаторы ресурсов.
- Telegram Bot API — best-effort уведомление после сохранения заказа.

Точные версии фиксируются lock-файлом проекта. Новая зависимость добавляется только при реальной необходимости и не должна дублировать уже выбранный инструмент.

## 5. Слои и направление зависимостей

```text
app (routes/pages/layouts)
        │
        v
module UI / actions / route handlers
        │
        v
module service + schemas + types
        │
        ├────────> server/integrations
        v
server/db (Prisma)
        │
        v
PostgreSQL

components/ui, shared  <── могут использоваться верхними уровнями
```

Правила:

1. `app` компонует экран и вызывает публичный интерфейс модуля, но не содержит бизнес-правил и прямых Prisma-запросов.
2. Route Handler или Server Action отвечает за транспорт: получение входа, проверку сессии, вызов сервиса, преобразование результата.
3. `service.ts` содержит бизнес-операции и транзакционные границы.
4. Prisma разрешён в серверной части модуля и `src/server`, но никогда в Client Component.
5. Модуль не импортирует внутренние файлы другого модуля. Если взаимодействие нужно, используется его явно экспортированная серверная функция или небольшой общий контракт.
6. `shared` не импортирует `modules` и `app`. UI-примитивы не знают о товарах, заказах или Prisma.
7. Циклические импорты запрещены. Нельзя создавать общий `shared`, который фактически содержит бизнес-логику разных модулей.

Для дополнительной защиты серверные файлы помечаются `import "server-only"`. Клиентские entry points не должны реэкспортировать серверные функции.

## 6. Frontend

### Server и Client Components

По умолчанию страницы, layout и компоненты являются Server Components. Они читают каталог и настройки непосредственно через серверные query-функции модулей. Это уменьшает клиентский JavaScript и исключает лишний HTTP-запрос при первом рендере.

`"use client"` нужен только для интерактивных островов: Cart Drawer, изменение количества, фильтры с мгновенным UI, формы React Hook Form, Zustand, TanStack Query и анимации.

Frontend отвечает за:

- отображение данных и пользовательские взаимодействия;
- предварительную валидацию формы и понятные сообщения;
- локальное состояние UI;
- гостевую корзину `{ productId, quantity, selectedOptions?, observedPrice }` в Zustand/localStorage;
- повторную загрузку/инвалидацию клиентского кеша после мутаций.

Frontend не решает, можно ли оформить заказ, какова итоговая цена, допустим ли переход статуса или имеет ли пользователь административные права.

### Категории, карточки и глобальная навигация

- Диваны, стулья, посуда и следующие товарные категории принадлежат домену `catalog`, а не образуют отдельные бизнес-модули.
- `src/app/(store)/catalog/<category>/page.tsx` задаёт маршрут, metadata и композицию страницы; типы, данные и представления товара остаются в `modules/catalog`.
- Явные страницы допустимы для небольшого числа визуально отличающихся curated-категорий. Динамический `catalog/[category]` вводится после перехода к данным из БД и только когда он устраняет подтверждённое дублирование.
- Общие представления товара (`ProductPreview`, `ProductGallery`, `ProductConfigurator`) размещаются в `modules/catalog/components` и переиспользуются главной, каталогом, категориями и страницей товара. Отдельная категория не создаёт собственную дублирующую карточку.
- Статус новинки является временным маркетинговым состоянием товара: nullable `newFrom` и `newUntil` передаются как ISO 8601 UTC-строки в mock/DTO-контракте, а чистая функция каталога проверяет включительный интервал и сортирует активные новинки по `newFrom` от новых к ранним. `createdAt` и `updatedAt` не определяют этот статус.
- Акции принадлежат отдельному домену `promotions`: `Promotion` хранит период, процент скидки и явный список товаров, а чистая функция получает дату и каталог, отбирает активные предложения, рассчитывает готовые `PromotionalProduct` и детерминированно оставляет не более одной акции на товар. На mock-этапе приоритет задают `featured`, больший процент, более ранний старт и стабильный `id`; React-компоненты не пересчитывают коммерческую цену.
- `components/layout` содержит глобальный каркас и интерактивную навигацию: Header, mega-menu каталога, mobile navigation и переходы между маршрутами. Layout может компоновать публичный UI модулей и ссылки на доменные маршруты, но не получает цены, остатки и другие бизнес-данные напрямую.
- Анимация, пропорции изображения, hover quick view и визуальное число колонок являются UI-решениями из `docs/DESIGN.md` и не меняют архитектурные границы.

### Состояние и данные

- URL/search params — источник истины для фильтров и сортировки каталога, чтобы ссылки были воспроизводимы.
- Server Components — предпочтительный способ первичного чтения.
- TanStack Query — для динамических клиентских областей и мутаций, а не как обязательная обёртка над каждым запросом.
- Zustand — только состояние браузера. Нельзя копировать туда весь каталог, сессию или серверный кеш.
- localStorage считается недоверенным вводом: после восстановления корзина проходит Zod-проверку и серверную сверку.

### Временный mock-слой

- `mock-data.ts`, `mock-transport.ts` и preview session providers имитируют будущие контракты только на frontend/mock-этапе.
- Mock-функция остаётся типизированной и асинхронной, если production-потребитель также будет асинхронным, но искусственная задержка и хранение в памяти не переносятся в server/service слой.
- При подключении backend UI сохраняет безопасный DTO-контракт, а источник данных заменяется на query/service/transport соответствующего модуля.
- Наличие mock-реализации не означает, что API, авторизация, база данных, транзакция или интеграция уже реализованы и безопасны для production.
- Публичная `/sale` является только mock-витриной. Перед production-оформлением серверный pricing service обязан повторно проверить период и применимость акции, рассчитать цену по актуальным данным и сохранить в позиции заказа снимок итоговой цены и идентификатор применённой акции; значения из UI, Zustand и localStorage не являются источником истины.
- После фактической замены mock-файл удаляется; параллельная production- и mock-ветка одной бизнес-операции без отдельного тестового сценария не поддерживается.

## 7. Backend и API

Backend — серверная часть того же Next.js-приложения: Route Handlers, Server Actions, серверные query/service-функции и интеграции.

### Когда использовать Server Action

- мутация из формы, принадлежащей этому приложению;
- CRUD в админке;
- изменение статуса заказа или настроек;
- когда внешний публичный HTTP-контракт не нужен.

### Когда использовать Route Handler

- запрос из TanStack Query или другого независимого клиента;
- проверка корзины и создание заказа через JSON;
- Auth.js callbacks;
- подпись прямой загрузки Cloudinary;
- будущие webhooks платежей и внешних систем.

Нельзя реализовывать одну бизнес-операцию отдельно и в Action, и в Route Handler. Оба транспорта при необходимости вызывают один `service`.

### Организация HTTP API

- Базовый namespace: `/api`.
- Ресурсные имена во множественном числе: `/api/products`, `/api/orders`.
- Фильтры — query-параметры с единой Zod-схемой.
- Нестандартная операция — явный endpoint, например `/api/cart/validate`; не RPC-набор без причин.
- Успех возвращает DTO, а не Prisma-модель.
- Ошибка имеет стабильную форму:

```ts
type ApiError = {
  error: {
    code: string;
    message: string;
    fieldErrors?: Record<string, string[]>;
    requestId?: string;
  };
};
```

Ориентиры по статусам: `400` неверный ввод, `401` нет сессии, `403` нет прав, `404` ресурс не найден, `409` конфликт/устаревшая цена, `422` бизнес-ограничение, `500` непредвиденная ошибка.

API не считается границей безопасности само по себе: каждый защищённый handler/action повторно проверяет сессию и роль.

## 8. База данных

PostgreSQL — источник истины для товаров, актуальных цен, доступности, заказов, настроек магазина и
административной identity. Покупательские аккаунты и их корзины добавляются с этапа 2. Prisma schema
и миграции — исполняемое описание структуры БД. Базовая PostgreSQL schema, модели каталога и настроек,
их первая версионируемая миграция и единый server-only PrismaClient уже настроены.

Минимальная модель MVP:

- `Product`: id, slug, name, description, price (`Decimal`), stock, isActive, nullable newFrom/newUntil, material, style, dimensions, rating при необходимости, timestamps.
- `ProductImage`: id, productId, cloudinaryPublicId, secureUrl, alt, position.
- `Category`: id, slug, name; связь с товарами.
- `ProductOptionGroup`: id, productId, stable key, label, position.
- `ProductOption`: id, groupId, stable key, label, position.
- `Order`: id, publicNumber, customerName, phone, email, comment, total, status, timestamps, optional userId.
- `OrderItem`: orderId, productId nullable, snapshotName, snapshotPrice, quantity, snapshotOptions, lineTotal.
- `OrderStatusHistory`: orderId, previousStatus, newStatus, changedByUserId, createdAt.
- `StoreSettings`: singleton/именованные настройки магазина и контакты.
- Основные настройки адресуются стабильным уникальным ключом `primary`; каталог индексируется под
  активную общую выборку, выборку категории и период новинки, а дочерние данные товара имеют
  уникальные позиции внутри родителя и составные области уникальности стабильных ключей.
- таблицы Auth.js `User`, `Account`, `Session`, `VerificationToken` и `User.role` для административной
  авторизации. Auth identity использует строковый `cuid`; adapter-модель database session хранит
  только уникальный случайный `sessionToken`, срок действия и ссылку на пользователя, но первый
  административный Credentials-провайдер использует обязательную для Auth.js 5 JWT strategy.
  OAuth-токены остаются внутри
  `Account` и не пересекают публичные DTO. `User.role` использует закрытый enum `USER | ADMIN` с
  безопасным default `USER`; optional `passwordHash` хранится только для Credentials identity, а
  optional `phone` не участвует в идентификации. Канонический `User.email` сохраняется после
  server-side `trim` и lowercase и остаётся уникальным; клиент не может назначать роль или hash.
  Миграция Auth.js создаёт unique/primary индексы для поиска по email, provider account и session
  token, а также отдельные индексы внешних ключей `Account.userId` и `Session.userId` для relation
  lookup и каскадного удаления.

Этап 2 добавляет `Cart`, `CartItem` и пользовательские сценарии. Не нужно создавать их для гостевой корзины MVP, если пользовательская авторизация ещё не реализована.

### Решения первого DB-релиза

- `Order.status` использует только значения `NEW`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED` и
  `CANCELLED`.
- Товарные опции представлены группами и значениями. `ProductVariant` и отдельные SKU для комбинаций
  опций в первый релиз не входят; такая сущность добавляется отдельной миграцией, только когда
  комбинации потребуется собственный SKU, цена или остаток.
- Денежные значения хранятся как PostgreSQL `numeric` и Prisma `Decimal`. Публичный денежный DTO имеет
  форму `{ amount: string; currency: "BYN" }`, где `amount` — каноническая decimal-строка, а не
  JavaScript `number` и не сериализованный Prisma-тип.
- Auth.js сначала обслуживает администратора. Пользовательская авторизация и постоянная серверная
  корзина относятся к следующему этапу; гостевая корзина до этого остаётся клиентской.
- Установленный Auth.js 5 разрешает Credentials-вход только с JWT session strategy. Административная
  сессия поэтому хранится в зашифрованной `HttpOnly` cookie не более 8 часов, содержит только id и
  роль, а `requireAdmin()` перед каждой защищённой операцией повторно читает актуальную роль из БД.
  Adapter-таблицы сохраняются для будущих провайдеров и не имитируют database session вручную.

### Retention, удаление аккаунта и bootstrap администратора

- Заказы и их снимки не удаляются каскадно вместе с пользователем, администратором или товаром.
  До юридического подтверждения меньшего срока применяется консервативное хранение 10 лет после
  окончания календарного года терминального статуса; legal hold имеет приоритет.
- Удаление аккаунта отзывает сессии и credentials, удаляет корзину, отвязывает заказы через nullable
  FK и необратимо анонимизирует профиль. Заказ сохраняет минимально необходимый контактный снимок до
  собственного retention-срока, затем прямые идентификаторы и свободный комментарий очищаются.
- Первый `ADMIN` создаётся отдельной server-only CLI-командой через direct DB connection и скрытый
  password input. Seed, миграции, CLI-аргументы, Git и логи не содержат credentials; команда
  под transaction-level DB lock создаёт администратора только при отсутствии любого `ADMIN` и
  повторно безопасна.
- Полная политика, последствия для будущей schema и критерии проверки описаны в
  `docs/first-db-release-decisions.md`, пункт 25.

Ключевые правила БД:

- Деньги — `Decimal`/`numeric`, никогда `float`; валюта задаётся явно.
- Заказ хранит снимки имени, цены и опций товара: последующее редактирование товара не меняет историю заказа.
- Удаление товара, попавшего в заказ, выполняется как деактивация (`isActive=false`) либо допускает nullable FK; история заказа не удаляется.
- Все FK, unique-ограничения, обязательность, enum статусов и нужные индексы задаются в схеме.
- Создание `Order` и всех `OrderItem`, вычисление total и очистка серверной корзины выполняются в одной транзакции.
- Миграции версионируются; production-схема не меняется через ручной `db push`.
- БД обеспечивает целостность, но бизнес-переходы статусов и проверку актуальности выполняет service-слой.

Prisma-типы не являются публичными DTO. Перед отправкой в браузер удаляются служебные поля, `Decimal` преобразуется в согласованный строковый формат, даты — ISO 8601.

Публичные allowlist-контракты каталога и настроек расположены в `src/modules/catalog/server/dto.ts` и
`src/modules/settings/server/dto.ts`. Строгие Zod-схемы отклоняют неизвестные поля, ограничивают
размеры строк и коллекций и допускают только JSON-сериализуемые значения. Каталог публикует строковые
идентификаторы, slug, контент, изображения без Cloudinary public id, ISO 8601 даты и денежный объект;
настройки — только название, описание, контакты и безопасные публичные ссылки. Первичные/внешние ключи
БД, `key`, остатки, флаги публикации и timestamps не входят в эти DTO.

Server-only mapper каждого доменного модуля является единственной границей между Prisma-shaped
результатом query и публичным DTO service. Mapper каталога преобразует `BigInt` и cursor id в строки,
даты — в ISO 8601 UTC, `Decimal` — в `MoneyDto`, а внутренние ключи групп и опций — в стабильные
публичные идентификаторы; mapper настроек повторно валидирует недоверенные JSON-колонки. Каждый
сформированный объект проходит соответствующую строгую Zod-схему, поэтому неполная или повреждённая
запись БД не выдаётся как частично валидный публичный объект.

Общий денежный контракт расположен в `src/shared/money.ts`: `MoneyDto` содержит каноническую
неотрицательную decimal-строку с двумя знаками после точки и явную валюту `BYN`. Mapper принимает
Prisma-compatible Decimal-like значение, но возвращает только проверенный JSON-safe DTO. На период
перехода formatter принимает как `MoneyDto`, так и прежний frontend `number`; это не делает клиентское
число доверенным источником цены и не разрешает использовать его в серверных расчётах заказа.

## 9. Основные потоки данных

### Просмотр каталога

```text
URL filters -> Server Component -> catalog service -> query -> Prisma -> PostgreSQL
                                        |
                                        v
                              mapper -> Product DTO -> HTML/React
```

Фильтры валидируются сервером. Запрос возвращает только активные товары, использует пагинацию и индексируемые поля.

### Гостевая корзина

```text
Product DTO -> Zustand -> persist/localStorage
                    |
открытие корзины ---┴-> POST /api/cart/validate -> cart service -> Product в БД
                                                     |
                                                     v
                           актуальная цена/доступность/изменения
```

Клиент хранит идентификаторы и наблюдаемую цену только для UX. Итог всегда пересчитывается сервером.

### Оформление заказа

```text
Checkout form + cart ids
  -> Zod на клиенте
  -> POST /api/orders
  -> Zod + rate/abuse protection по мере необходимости
  -> order service
  -> повторное чтение Product + проверка stock/isActive/options/price
  -> при изменении цены: 409 + список изменений для подтверждения
  -> Prisma transaction: Order + OrderItem + initial history
  -> commit
  -> ответ клиенту с номером заказа
  -> Telegram notification (best effort)
```

Сбой Telegram не откатывает уже созданный заказ. Ошибка логируется, заказ остаётся виден в админке — это основной канал уведомления согласно ТЗ. Если гарантированная доставка уведомлений станет требованием, позже добавляется outbox/очередь, но не сейчас.

### Изменение статуса администратором

```text
Admin form -> Server Action -> auth() + role ADMIN -> Zod
  -> orders service -> проверка разрешённого перехода
  -> transaction: Order.status + OrderStatusHistory
  -> revalidatePath / Query invalidation -> UI
```

Разрешены `NEW -> CONFIRMED -> IN_PROGRESS -> COMPLETED`, а также переходы в `CANCELLED` из
`NEW`, `CONFIRMED` и `IN_PROGRESS`. Остальные переходы отклоняются сервером.

### Загрузка изображения

```text
Admin UI -> server получает подпись после проверки ADMIN
  -> браузер загружает файл напрямую в Cloudinary
  -> admin form отправляет publicId/secureUrl/metadata
  -> backend валидирует и сохраняет ProductImage
```

Сервер не проксирует большие файлы без необходимости. Удаление/замена изображения координируется адаптером Cloudinary; при частичном сбое должна быть возможность повторить очистку.

## 10. Бизнес-логика и валидация

Бизнес-логика находится в `src/modules/<module>/service.ts` и чистых функциях того же модуля:

- серверный расчёт цены и total;
- доступность и остаток товара;
- сверка корзины;
- снимки позиций заказа;
- транзакционное создание заказа;
- допустимые переходы статуса;
- объединение гостевой и пользовательской корзин на этапе 2;
- правила доступа к пользовательским данным.

Валидация выполняется на трёх уровнях:

1. Клиент: React Hook Form + та же Zod-схема для быстрого UX.
2. Серверная граница: обязательный `safeParse` любого body, params, query, FormData, localStorage payload и ответа внешнего API.
3. БД: типы, NOT NULL, unique, FK, enum и check constraints, где Prisma/PostgreSQL позволяют выразить инвариант.

Клиентская проверка никогда не заменяет серверную. Схема входа размещается в соответствующем модуле, чтобы transport, форма и тесты использовали один контракт. Схемы БД и DTO не смешиваются: Zod input описывает допустимый ввод, Prisma — хранение, mapper — выдачу.

## 11. Типы, схемы, конфигурация и утилиты

- Тип, нужный одному модулю, живёт в `modules/<module>/types.ts`.
- Zod-схема конкретного сценария — в `modules/<module>/schemas.ts`.
- DTO формируется явно и не выводится автоматически из полной Prisma-модели для клиента.
- Межмодульный маленький контракт может находиться в `shared/types`, но переносить туда всё заранее нельзя.
- Несекретные настройки приложения — `shared/config`; env-зависимые настройки — `server/env.ts`.
- Константы конкретного домена остаются в модуле; `shared/constants` только для реально общих значений.
- `shared/utils` содержит чистые, доменно-нейтральные функции. Файлы `helpers.ts` без ясной области ответственности запрещены.
- Алиасы импортов (`@/...`) предпочтительнее длинных относительных путей.

## 12. Ошибки, логирование и наблюдаемость

Ошибки разделяются на ожидаемые и непредвиденные:

- ожидаемые (`ValidationError`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, бизнес-ошибка) преобразуются transport-слоем в стабильный код и безопасное сообщение;
- непредвиденные логируются на сервере с контекстом/requestId, клиент получает общее сообщение без stack trace, SQL и секретов.

UI использует `error.tsx`, `global-error.tsx`, `not-found.tsx`, состояния ошибок форм и retry там, где операция безопасна. Ошибка одной карточки/интерактивной зоны по возможности не ломает весь экран.

Нельзя логировать пароли, session tokens, API keys, полный Authorization header и избыточные персональные данные заказа. Для production в будущем можно подключить Sentry/структурированные логи, но отдельная технология не обязательна для MVP.

## 13. Аутентификация и доступ

Для MVP Auth.js обязателен для администратора. Роли:

- `GUEST`: просмотр каталога, гостевая корзина, создание заявки;
- `USER`: этап 2 — профиль, собственные заказы и серверная корзина;
- `ADMIN`: CRUD товаров, заказы, статусы, настройки магазина.

Правила:

- пароль хранится только как versioned salted `scrypt` hash (`N=16384`, `r=8`, `p=1`, 64-byte key);
  открытый пароль в БД и логах запрещён;
- session cookie — `HttpOnly`, `Secure` в production, подходящий `SameSite`;
- `middleware.ts` может сделать ранний redirect, но окончательная проверка `auth()` и роли выполняется в каждом Server Action/Route Handler/service entry point;
- скрытие кнопки не является авторизацией;
- объект пользователя всегда проверяется по `userId` на владение ресурсом;
- административный URL сам по себе не секрет и не механизм защиты;
- защита от CSRF опирается на безопасные механизмы Auth.js/Server Actions и проверку origin для чувствительных HTTP endpoint;
- login и создание заказа должны иметь защиту от перебора/спама. Простую платформенную rate limit можно подключить, когда приложение выходит в публичный доступ; Redis только ради этого заранее не нужен.

Пользовательские аккаунты и восстановление пароля входят в этап 2. До появления полноценной почтовой интеграции нельзя обещать email-восстановление. Telegram-восстановление не добавляется без отдельной модели привязки и проверки владения аккаунтом.

## 14. Переменные окружения и server-only код

Пример набора имён (без значений):

```dotenv
DATABASE_URL=
DATABASE_URL_UNPOOLED=
AUTH_SECRET=
AUTH_URL=
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
TELEGRAM_BOT_TOKEN=
TELEGRAM_ADMIN_CHAT_ID=
OPENAI_API_KEY=
```

`OPENAI_API_KEY` добавляется только на этапе AI. Конкретные имена Auth.js зависят от фактически установленной версии и проверяются по её документации.

Правила:

- `.env*` с секретами не коммитятся; `.env.example` содержит только имена и безопасные подсказки;
- `server/env.ts` валидирует env при старте/сборке и выдаёт понятную ошибку;
- только значения с префиксом `NEXT_PUBLIC_` могут попасть в клиент, и среди них не должно быть секретов;
- Prisma client, `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, Auth config/secret, Cloudinary secret,
  Telegram token, OpenAI key, проверка ролей, бизнес-правила, расчёты заказа и доступ к БД — строго
  server-only;
- секреты на Vercel/сервере задаются средствами окружения, а не в Docker image или репозитории.

## 15. Статические и пользовательские файлы

- `public/` — только версионируемые статические ресурсы приложения.
- На текущем mock-этапе демонстрационные фотографии товаров и интерьеров хранятся в `public/images` и версионируются вместе с интерфейсом.
- Локальные фотографии товара группируются по правилу `public/images/<category-slug>/<product-slug>/<position>-<role>.<extension>`; порядок галереи задаётся данными товара, а не чтением файловой системы.
- В production управляемые фотографии товаров загружаются в Cloudinary; новые пользовательские загрузки не коммитятся и не хранятся в PostgreSQL как binary/base64.
- Статические брендовые изображения и неизменяемые ресурсы интерфейса могут оставаться в `public/`, если им не нужен административный жизненный цикл.
- В БД: `publicId`, URL, alt, размер/формат при необходимости и порядок в галерее.
- Upload принимает только разрешённые MIME-типы и ограничения размера; имя клиента не используется как безопасный путь.
- Изображения выводятся через `next/image`; домен Cloudinary разрешается в `next.config.ts`.
- Для удаления товара предпочтительна деактивация. Физическое удаление внешних изображений выполняется только после проверки, что ресурс больше нигде не используется.

## 16. Сборка и развёртывание

### Основной production-вариант: Vercel

Один Git-репозиторий и один Next.js deployment. PostgreSQL размещается в Neon через Neon-managed
Vercel Integration, Cloudinary остаётся управляемым внешним сервисом. Runtime использует pooled
`DATABASE_URL`, а отдельный migration job — direct `DATABASE_URL_UNPOOLED`. Pipeline:

```text
Pull Request -> install from lock-file -> lint -> unit/integration tests -> build -> preview
main         -> те же проверки -> prisma migrate deploy -> production deploy -> smoke/e2e
```

Миграции выполняются один раз сериализованным release-шагом через direct connection до rollout, а не
во время build, старта или serverless cold start. Перед несовместимыми изменениями применяется
expand/migrate/contract: сначала совместимая схема, затем код/данные, затем удаление старого поля.

Для self-hosting позже можно добавить Dockerfile с `next build`/standalone output и запуском Node.js.
Docker не нужен для первого Vercel-развёртывания и не меняет модульную архитектуру. Production
использует защищённую Neon-ветку, каждый preview — отдельную ephemeral-ветку, local — отдельную
dev-ветку. Preview/local не получают production credentials или немаскированные production-данные.
Полные правила зафиксированы в `docs/first-db-release-decisions.md`.

Обязательные проверки перед релизом: TypeScript/`next build`, ESLint, Jest, критические Playwright-сценарии, валидные миграции. Seed не запускается автоматически в production.

## 17. Добавление функций и модулей

### Новый сценарий существующего домена

1. Добавить/изменить Zod input в модуле.
2. Реализовать бизнес-операцию в service или чистой функции.
3. При необходимости добавить Prisma migration.
4. Подключить один транспорт: Server Action или Route Handler.
5. Добавить UI в модуль и скомпоновать страницу в `app`.
6. Покрыть бизнес-правило unit/integration-тестом и критический путь E2E.
7. Обновить этот документ, если меняется граница или направление зависимости.

### Новый домен

Создать `src/modules/<name>` с минимально нужными файлами. Модуль владеет своими схемами, сервисами и UI. Он не должен требовать правок во множестве существующих модулей: маршруты добавляются в `app`, интеграция выполняется через небольшой публичный контракт.

### Примеры развития

- `reviews`: отдельные таблицы и модуль, catalog получает агрегированный рейтинг через публичную query-функцию/денормализованное поле только после измерения.
- `payments`: модуль payment с provider adapter и webhook route; заказ остаётся владельцем статуса исполнения, payment — статуса транзакции.
- `assistant`: серверный модуль получает ограниченный каталог через catalog API функции; ключ и системные инструкции не попадают в браузер.
- `analytics`: сначала события и внешний провайдер; отдельное хранилище только при фактическом объёме.

## 18. Допустимые и запрещённые зависимости

Допустимо:

- `app -> modules -> server/db|integrations`;
- любой верхний слой -> `shared` и `components/ui`;
- серверный модуль -> публичный серверный контракт другого модуля для конкретного сценария;
- Client Component -> клиентский API/Action wrapper и безопасные DTO.

Следует избегать:

- Client Component -> Prisma, env secrets, server integration;
- `shared -> modules` или `shared -> app`;
- импорт внутренних файлов соседнего модуля по глубокому пути;
- `app/api` с продублированной бизнес-логикой;
- прямой SQL/Prisma из UI-компонента;
- универсальный глобальный store для всех данных;
- двунаправленные зависимости `catalog <-> orders`; order service читает каталог через узкий публичный контракт или согласованную серверную функцию;
- barrel-файлы, которые смешивают client/server exports;
- зависимость бизнес-логики от React, HTTP `Request`/`Response` или конкретного внешнего SDK.

### Известные переходные отклонения

На mock-этапе существуют глубокие межмодульные импорты: каталог использует store корзины, cart и admin читают mock-данные catalog, auth и checkout используют внутренние контракты cart, а layout напрямую компонует CartWidget. Они допустимы только как зафиксированный переходный долг и не отменяют правила публичных контрактов.

При переводе затронутого сценария на production:

1. Определи минимальный контракт, который действительно нужен внешнему потребителю.
2. Создай публичный client entry point (`public.ts`) или server-only entry point (`server.ts`) только при наличии такого потребителя.
3. Не смешивай client и server exports в одном barrel-файле.
4. Переведи потребителей с глубоких импортов на публичный контракт и удали заменённый mock-путь.
5. Не добавляй новые глубокие межмодульные импорты, ссылаясь на существующие временные отклонения.

Когда количество таких зависимостей начнёт расти, границы следует закрепить существующим ESLint через `no-restricted-imports`; новая библиотека для проверки архитектуры требует отдельного решения.

## 19. Потенциальное масштабирование

Сначала масштабируется единое stateless Next.js-приложение горизонтально, PostgreSQL — через индексы, pooling и оптимизацию запросов, Cloudinary — независимо как managed storage/CDN.

Без серьёзной переделки в будущем можно вынести:

- Telegram/email уведомления — за адаптером интеграции; очередь/outbox нужна только при требовании гарантированной доставки или большом объёме;
- AI assistant — изолированный модуль с отдельными лимитами и провайдером;
- платежные webhooks/обработку — отдельный worker/service при росте;
- поиск — внешний search engine, если PostgreSQL-поиска и индексов станет недостаточно;
- обработку медиа — уже отделена Cloudinary;
- read-heavy API каталога — отдельный сервис только после появления независимой нагрузки/команды/релизного цикла.

Условие выделения — измеренная нагрузка, разные требования к отказоустойчивости или независимый жизненный цикл, а не предполагаемый рост.

## 20. Непреложные архитектурные правила

1. Один модульный Next.js-монолит остаётся базовой единицей до появления измеренной причины разделения.
2. Бизнес-правила не находятся в страницах, компонентах, Route Handlers или Prisma hooks.
3. Любой недоверенный ввод повторно валидируется на сервере Zod-схемой.
4. Цена, доступность, остаток, total и права доступа определяются только сервером.
5. Заказ создаётся транзакционно и хранит снимки товарных данных.
6. PostgreSQL — источник истины; Zustand/localStorage и TanStack Query — лишь клиентское состояние и кеш.
7. Секреты, Prisma и внешние privileged SDK никогда не входят в клиентский bundle.
8. Административное действие всегда проверяет сессию и роль на сервере.
9. Модули взаимодействуют через узкие явные контракты; циклы и глубокие межмодульные импорты запрещены.
10. Не вводятся лишние слои и инфраструктура без текущего сценария и понятной выгоды.
11. Изменение БД выполняется миграцией и сопровождается проверкой обратной совместимости релиза.
12. Критические бизнес-потоки — оформление заказа, смена статуса и права администратора — покрываются тестами.
13. Ошибки клиенту безопасны и стабильны; технические детали остаются в серверных логах.
14. `architecture.md` обновляется одновременно с архитектурно значимым изменением кода.

## 21. Решения, отложенные до появления потребности

- Redis, очередь и outbox — при гарантированной асинхронной доставке или измеренной нагрузке.
- Отдельный backend — при наличии второго крупного клиента, независимой команды/релизов или несовместимого профиля масштабирования.
- Docker — для self-hosting, не обязателен на Vercel.
- Платёжный провайдер, почтовый сервис, Sentry, внешний поиск — внедрять на соответствующем этапе и после выбора конкретных требований.
- OpenAI API — только этап 3; все обращения выполняются сервером с лимитами, валидацией ответа и контролем стоимости.

До наступления этих условий новые технологии не являются частью обязательной архитектуры.
