# План внедрения базы данных

## 1. Назначение

Этот документ детализирует пункты 39–49 из `docs/implementation-plan.md` и их зависимости от
backend-пунктов 23–38. Он описывает подготовку перехода с текущих mock-данных на PostgreSQL через
Prisma, но не означает, что база данных, Prisma schema или серверные сценарии уже реализованы.

Основные источники решений:

1. `docs/implementation-plan.md` — порядок продуктовых задач;
2. `docs/architecture.md` — границы модулей, потоки данных и production-ограничения;
3. `docs/TermsOfReference.md` — продуктовые сущности и сценарии;
4. фактические типы, схемы и mock-transport в `src/modules/**` — текущее поведение UI.

При расхождении документации и кода решение сначала согласуется и фиксируется в архитектуре, после
чего выражается в Prisma schema, миграции, серверном контракте и тестах.

## 2. Текущее состояние

- Установлены Prisma `7.9.1`, `@prisma/client`, `@prisma/adapter-pg` и `pg`.
- В `.env.example` предусмотрен `DATABASE_URL` без значения.
- В `package.json` есть команды `prisma:validate`, `prisma:generate`, `prisma:migrate` и
  `prisma:studio`.
- `prisma/schema.prisma`, Prisma config, миграции и DB client пока отсутствуют.
- Каталог, авторизация, профиль, корзина, checkout и админка используют типизированные mock-слои,
  `localStorage`, `sessionStorage` или память процесса.
- PostgreSQL ещё не является фактическим источником истины, поэтому DB-пункты 39–49 не считаются
  реализованными.

## 3. Границы будущего решения

Сохраняется модульный монолит:

```text
app -> публичный server-контракт модуля -> service/query -> Prisma -> PostgreSQL
                                      -> mapper -> безопасный DTO -> UI/API
```

- `src/app` не содержит бизнес-правила и прямые Prisma-запросы.
- Server-only DB-инфраструктура размещается в `src/server`.
- Доменные запросы и services размещаются внутри соответствующих `src/modules/<domain>`.
- Prisma-модели не передаются в Client Components и публичные API.
- Отдельный универсальный repository-слой над Prisma заранее не создаётся. Узкие query/service-функции
  добавляются по фактическим сценариям.
- Zustand, localStorage и TanStack Query остаются состоянием и кешем, но не источником истины.

## 5. Целевая модель данных

Перечень ниже задаёт направление проектирования, но не заменяет будущую Prisma schema.

### 5.1 Пользователи и Auth.js — пункт 39

- `User`: профиль, уникальный нормализованный email, optional phone, роль и timestamps.
- `Account`, `Session`, `VerificationToken`: структура должна соответствовать выбранному Auth.js
  adapter и фактической стратегии авторизации.
- `UserRole`: как минимум `USER` и `ADMIN`.
- `passwordHash` добавляется только при подтверждённой Credentials-стратегии; пароль, reset token и
  session token никогда не входят в публичный DTO.
- Публичная регистрация не может назначать роль администратора.

Auth.js-модели можно предусмотреть в общей схеме, но пользовательские сценарии из этапа 2 не должны
задерживать подключение публичного каталога и гостевого заказа MVP.

### 5.2 Каталог — пункт 40

- `Category`: уникальные `slug` и название, optional порядок отображения и active-флаг.
- `Product`: уникальный `slug`, название, описание, точная цена, валюта, остаток, состояние публикации,
  category и timestamps.
- `ProductImage`: product, Cloudinary metadata/URL, alt и position.
- `ProductSpecification`: product, label, value и position.
- `ProductVariant`: product, optional SKU, точная цена/price override, остаток и active-флаг — только
  если комбинация опций действительно является отдельной складской единицей.
- Опции конфигурации должны иметь стабильные ID, совпадающие с контрактом корзины; конкретная
  нормализация option groups/options определяется после решения по вариантам.

Поля `material`, `style`, `dimensions`, `color` и `rating` не следует автоматически превращать в
отдельные таблицы. Нормализация выбирается по реальным фильтрам, редактированию и требованиям
целостности.

### 5.3 Корзина — пункт 41

- `Cart`: принадлежит пользователю; для MVP предполагается не более одной активной корзины на user.
- `CartItem`: cart, product или variant, quantity и наблюдаемая пользователем цена.
- Выбранная конфигурация хранится в нормализованных связях либо каноническом JSON только после
  утверждения модели вариантов.
- Уникальность позиции определяется сочетанием cart, product/variant и конфигурации.

Гостевая корзина продолжает храниться в Zustand/localStorage. При входе сервер валидирует её позиции,
объединяет их с `Cart` и возвращает безопасный DTO. Клиентские цена, доступность и quantity считаются
недоверенными.

### 5.4 Заказы — пункты 42 и 44

- `Order`: public number, optional user, контакты покупателя, comment, точная total, currency, status и
  timestamps.
- `OrderItem`: optional ссылка на product/variant и обязательные снимки названия, конфигурации,
  unit price, quantity и line total.
- `OrderStatusHistory`: order, previous status, new status, optional admin и createdAt.

Создание заказа выполняется атомарно:

```text
повторная валидация товаров и цены
-> транзакция: Order + OrderItem[] + initial history + остатки + очистка server cart
-> commit
-> уведомление Telegram вне транзакции
```

Редактирование или деактивация товара не изменяет снимки уже созданного заказа.

### 5.5 Настройки — пункт 43

- `StoreSettings`: уникальный стабильный ключ, название, описание, контакты, адрес, часы работы и
  социальные ссылки.
- Для единственного магазина используется именованная запись, например `default`, а не неявное
  предположение о числовом ID.
- Публичное чтение возвращает только разрешённые поля; изменение выполняется после server-side
  проверки роли администратора.

## 6. Инварианты и типы — пункт 45

- Денежные значения хранятся как PostgreSQL `numeric`/Prisma `Decimal`, не как float.
- Валюта хранится явно; MVP поддерживает `BYN`.
- На публичной границе сумма сериализуется в согласованный DTO, предпочтительно decimal-строкой с
  валютой. Текущие frontend `number` требуют отдельного совместимого перехода.
- Email и slug уникальны в согласованной нормализованной форме.
- Quantity положительное, stock неотрицательный; необходимые `CHECK` constraints добавляются в SQL
  миграции, если не выражаются Prisma schema.
- FK и обязательность отражают возможность сохранения истории: пользователь и исходный товар могут
  стать недоступными, но заказ и его снимки остаются.
- Продукт, участвовавший в заказе, деактивируется вместо физического удаления.
- Переход статуса проверяется service-слоем и сохраняется вместе с history в одной транзакции.
- Read-modify-write операции с остатками и статусами защищаются условным атомарным обновлением,
  constraint или транзакцией.

### Предварительная политика удаления

| Связь                                 | Предварительное поведение                                                 |
| ------------------------------------- | ------------------------------------------------------------------------- |
| Product -> ProductImage/Specification | `Cascade`                                                                 |
| Cart -> CartItem                      | `Cascade`                                                                 |
| User -> Cart                          | управляемое удаление или `Cascade` после решения о lifecycle пользователя |
| User -> Order                         | `SetNull`, снимок покупателя сохраняется                                  |
| Product/Variant -> OrderItem          | nullable FK или `Restrict`, snapshots обязательны                         |
| Admin -> OrderStatusHistory           | `SetNull`, история сохраняется                                            |

Окончательное `onDelete` фиксируется только после описания сценария удаления пользователя и требований
к хранению заказов.

## 7. Индексы — пункт 46

Начальный набор подтверждается фактическими запросами:

- unique `Category.slug`, `Product.slug`, `User.email`;
- каталог: состояние публикации + category + порядок/createdAt;
- изображения и характеристики: parent ID + position;
- корзина: unique active cart по user и lookup items по cart;
- история пользователя: user + createdAt;
- административные заказы: status + createdAt;
- история статусов: order + createdAt.

Индекс не добавляется только потому, что поле существует. Для новых критичных запросов сначала
фиксируется фильтрация, сортировка и ожидаемый объём, затем при доступной непроизводственной БД
проверяется `EXPLAIN`.

## 8. Этапы внедрения

### Этап A — решения и окружение

1. Разрешить открытые вопросы из раздела 11.
2. Выбрать локальную, preview и production PostgreSQL-среду и способ pooling.
3. Подтвердить Auth.js strategy и требования Prisma `7.9.1` по локальной документации установленной
   версии.
4. Зафиксировать правила доступа к секретам и release-процесс миграций.

Результат: решения достаточны для создания schema без догадок.

### Этап B — Prisma foundation, каталог и настройки

Связанные пункты: 23, 24, 34, 40, 43, 45–48.

1. Создать Prisma config, `prisma/schema.prisma`, server-only `src/server/db.ts` и первую миграцию.
2. Описать Category, Product, изображения, характеристики и StoreSettings.
3. Перенести текущий стартовый каталог и настройки в повторяемый seed.
4. Добавить module query/service и mapper в DTO.
5. Перевести публичный каталог, страницу товара и настройки с mock на server data.
6. После проверки удалить только ставшие неиспользуемыми mock-ветки.

Это рекомендуемый первый исполняемый DB-этап: read-only сценарии проще проверить и они не требуют
сначала завершить авторизацию и заказы.

### Этап C — Auth.js и серверная корзина

Связанные пункты: 25, 26, 29, 39, 41, 45–49.

1. Добавить Auth.js-модели по официальной схеме выбранного adapter.
2. Реализовать server-side session и role checks.
3. Добавить Cart/CartItem и безопасное объединение гостевой корзины.
4. Заменить preview/sessionStorage gate и mock transports только после готовности реальной
   авторизации.

### Этап D — заказ и история статусов

Связанные пункты: 30–33, 35, 37, 42, 44–49.

1. Добавить Order, OrderItem и OrderStatusHistory.
2. Реализовать серверный перерасчёт и транзакционное создание заказа.
3. Реализовать конкурентно безопасное изменение остатков.
4. Реализовать переход статуса с проверкой роли и текущего статуса.
5. Отправлять Telegram-уведомление только после commit; сбой уведомления не откатывает заказ.

### Этап E — production readiness

Связанные пункты: 36–38, 47–49.

1. Проверить release-команду `prisma migrate deploy`; не запускать миграции при serverless cold start.
2. Подготовить preview-проверку миграции на восстановленной непроизводственной копии данных.
3. Проверить обязательные переменные окружения без вывода их значений.
4. Выполнить integration, smoke и производительные проверки основных запросов.
5. Описать backup/restore и forward-fix для несовместимых изменений.

## 9. Миграции — пункт 47

- Миграции создаются и версионируются вместе с использующим их кодом.
- Сгенерированный SQL читается до применения: проверяются `DROP`, type narrowing, `NOT NULL` без
  backfill, table rewrite, блокировки и изменение enum/constraint.
- `prisma db push` не заменяет миграции в разделяемых и production-средах.
- Для несовместимого изменения применяется `expand -> migrate -> contract` в нескольких deploy.
- Production migration выполняется один раз отдельным release-шагом.
- Destructive migration, reset, seed и production-запросы требуют отдельного разрешения.
- Пока целевая PostgreSQL-среда не определена, миграция не создаётся и не применяется.

## 10. Seed и проверки — пункты 48–49

Seed должен быть повторяемым и безопасным:

- использовать стабильные slug/keys и `upsert` там, где это соответствует данным;
- не удалять неизвестные или пользовательские записи;
- переносить каталог из текущих mock-данных через явный mapper;
- не хранить пароль администратора или другие credentials в Git;
- создавать администратора только из валидированных переменных окружения либо отдельной
  контролируемой команды;
- не запускаться автоматически при production deploy без явного решения.

Минимальные integration-проверки:

- duplicate email и slug отклоняются;
- inactive product отсутствует в публичной выдаче;
- удаление/деактивация товара не уничтожает историю заказа;
- заказ, позиции и initial history создаются полностью либо полностью откатываются;
- итог вычисляется по текущей серверной цене, а не по localStorage;
- недопустимый переход статуса отклоняется без частичной записи;
- конкурентные заказы не продают один последний остаток дважды;
- пользователь получает только свои cart/orders;
- административные операции требуют server-side роли;
- основные catalog/order запросы используют ожидаемые индексы на репрезентативных данных.

Новые E2E создаются только после отдельного разрешения. DB-инварианты преимущественно покрываются
unit- и integration-тестами.

## 11. Открытые решения перед созданием Prisma schema

1. Вариант товара — отдельный SKU с собственной ценой и остатком или только набор выбранных опций?
2. Какие характеристики участвуют в фильтрации и требуют нормализации: material, style, color,
   dimensions?
3. Какой канонический набор статусов заказа использовать? ТЗ и backend-пункт 33 описывают четыре
   статуса, а текущий UI содержит дополнительный `confirmed`.
4. Нужна ли регистрация пользователей в первом DB-релизе или Auth.js/user cart остаются этапом 2?
5. Какая политика удаления/анонимизации пользователя и срок хранения заказов?
6. Какая PostgreSQL-платформа используется локально, в preview и production, и какой pooling она
   требует для Vercel?
7. В каком формате деньги передаются в DTO: decimal-строка + currency либо integer minor units?
8. Как создаётся первый администратор без хранения credentials в репозитории?

Ответы фиксируются до первой миграции. Они не блокируют сохранение этого подготовительного плана.

## 12. Критерии готовности к реализации

DB-этап можно начинать, когда:

- согласованы открытые доменные решения;
- доступна непроизводственная PostgreSQL и известен deployment target;
- подтверждены Auth.js и Prisma-паттерны для установленных версий;
- определён первый вертикальный этап и его server DTO;
- описаны migration, seed и rollback/forward-fix границы;
- изменения можно проверить без доступа к production-данным.

После каждого этапа обновляются `docs/architecture.md`, `docs/ProductTour.md` при изменении
пользовательских сценариев и `docs/progress.md`. Пункт 49 считается завершённым только после
проверяемых integration-тестов и анализа основных запросов, а не после одного `prisma validate`.
