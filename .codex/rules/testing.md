# Тестирование и проверки

## Общие правила

- Jest используй для unit- и component/integration-тестов, Playwright — для критических E2E.
- Существующие тесты разрешено читать и запускать для диагностики.
- Для новой функциональности добавляй только важные unit- и component/integration-тесты,
  проверяющие наблюдаемое поведение и доменные правила.
- Не изменяй существующие тесты без явного разрешения пользователя. При падении сначала установи
  причину и исправь реализацию, если дефект находится в ней.
- Не удаляй и не ослабляй проверки, не увеличивай timeout и не обновляй snapshots только ради
  успешного результата.

## Playwright и E2E

- Самостоятельно разрешено изменять только `playwright.config.ts`.
- Без предварительного явного разрешения пользователя запрещено создавать, изменять, перемещать и
  удалять `tests/e2e/**`, E2E fixtures, helpers, mocks, snapshots и сохраняемые в проект E2E-артефакты.
- Падение E2E-теста не разрешает изменять тест. Сначала проверь реализацию, конфигурацию, сервер и
  окружение.
- Разрешение на один E2E-файл или сценарий не распространяется на остальные.
- Перед изменением E2E опиши сценарий, объясни, почему недостаточно unit/component/integration-теста,
  перечисли затрагиваемые файлы и дождись явного разрешения пользователя.

### Приоритетные E2E-сценарии Virtual Space

Предлагай E2E прежде всего для критических сквозных потоков:

1. Покупка: каталог → товар → конфигурация → корзина → checkout → подтверждение заказа.
2. Актуализация корзины: изменение цены или доступности → предупреждение → подтверждение или удаление
   позиции.
3. Авторизация и доступ: гость, пользователь и администратор; защита `/admin` и серверных операций.
4. Управление товаром: создание → загрузка изображения → публикация → редактирование → удаление.
5. Заказ: создание → `NEW → CONFIRMED → IN_PROGRESS → COMPLETED`, переход в `CANCELLED`, запрет
   недопустимых переходов и сохранение истории.

Не используй E2E для чистых функций, Zod-схем, Zustand actions, DTO, форматирования и изолированных
деталей UI — покрывай их unit- или component/integration-тестами.

## Обязательные проверки

- Минимальные проверки: `npm run lint`, `npm run typecheck`, затронутые тесты.
- Перед передачей по возможности запускай `npm test -- --runInBand` и `npm run build`.
- Для пользовательских потоков запускай существующие E2E через `npm run test:e2e`; для Prisma —
  проверки database rules.
- В отчёте укажи команды, результат и причины пропущенных проверок.
